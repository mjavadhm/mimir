# Peyda PM Bot development guide

Read `README.md` for product requirements and `docs/IMPLEMENTATION_PLAN.md` for delivery stages. Distinguish planned capabilities from verified results.

On 2026-11-21 the user required real testing from the first implementation phase. Each phase that reaches Telegram, Antigravity or GitHub is tried on that real service in the same phase. Offline tests stay separate and do not count as that check. Phase six is the integrated acceptance, not the first connection. Keep production rollout and PR review separate.

Read `docs/ARCHITECTURE.md` before planning or implementing a feature. It is the canonical contract for module ownership, public boundaries, transactions and the development workflow; keep the implementation plan consistent with it.

Keep routine tests offline and isolated from local `.env` and process credentials. Live checks are explicit commands, never part of routine pytest or import. Do not treat mock success as proof of real compatibility. CLI binaries, auth profiles, local databases and credentials belong in ignored `.tools/`, `.runtime/` and `.env`; never replace the existing `agy` GUI launcher.

Build from the current source and canonical documents. Do not inspect git history to infer delivered scope; this project is being built from scratch.

The Telegram topic is the persistent Antigravity conversation for the managed project. Each unread group line is typed into that chat with the speaker's identity, stable message/version reference and reply context. A waiting pile is one `session/prompt`, because each ACP prompt starts a full turn. Do not wrap the lines in a fresh system prompt or ask for JSON.

Group communication is explicit through additive Telegram tools during that same turn. The agent may send messages, reply to a chosen message, set/change/remove its own reaction, combine these, or remain silent. Reaction-only and silence are valid successful outcomes. Never require a final text, cap each turn to one group reply, auto-copy ordinary session text, or synthesize a fallback message after no text or a rejected reaction. Thoughts and tool traces remain in the private session view. Successful silent/reaction-only turns advance the durable cursor.

Live startup uses the regular `agy-cli` profile and launches ACP from the configured project root. Preserve the ordinary profile's tools, model/mode, permission settings, login, DBus and keyring behavior; do not add a file/terminal wrapper, a new filesystem sandbox, an overwrite ban, extra approval gates or automatic permission approval. Bind an existing conversation ID explicitly and fail startup if loading it fails. This reopens a conversation rather than attaching to a running interactive terminal. The ACP client does not advertise filesystem or terminal capability so agy uses its own tools; verify that behavior on the real CLI. Do not copy the bot's dedicated token or `PEYDA_*` variables into that process or tool configuration. This credential separation is not a filesystem isolation guarantee.

The recorded `tele-agy` reference at `ddaf8ad` concerns ACP input/transport, not a requirement to copy its output or queue. A group backlog is one turn with zero or more deliberate Telegram tool effects. Private-chat drafts are not used in the group topic.

## Architecture

- Deliver the management bot first, including its own live acceptance phase. Add automated PR review only in the separate second milestone described in `docs/PR_REVIEW_PLAN.md`. Reading PR status/links for coordination is in scope for management; diff analysis, findings, review publication and review-specific schema/scheduling are deferred. Review must not block the first milestone or create a second agent/session.

- Build in Python with aiogram 3. Keep a single modular application for the first version.
- Keep product rules in `domain`, use cases and I/O contracts in `application`, external integrations in `adapters`, and lifecycle management in `runtime`. Add modules when a delivered feature needs them, not as empty scaffolding.
- Domain code must not import aiogram, ORM models, API clients or subprocess code. Map external models into typed application data at boundaries.
- Wire concrete dependencies in `bootstrap`. Use small Protocols at real I/O boundaries and manual dependency injection. Prefer functions, dataclasses and composition; justify additional layers and design patterns with a concrete problem.
- Keep SQL in storage adapters and HTTP/ACP details in their own adapters. Avoid generic base repositories, service locators, speculative plugin systems and a single coordinator class that owns every responsibility.
- Group each layer by capability (`conversations`, `memory`, `work`, `actions`; `reviews` only later). Reuse the owning module instead of adding a parallel path. Cross-capability changes go through public application contracts, never another capability's ORM/repository internals.
- Route effects of bot-provided tools through the single action/policy/executor path; Telegram tools are a real consumer from phase two. This does not disable or intercept Antigravity's native shell, filesystem, git or `gh` tools. Do not claim that bot policies, deduplication or reconciliation govern every native command. Repositories do not commit independently; use-case transaction boundaries and a lightweight Unit of Work make related local writes atomic. Network calls remain outside those transactions.

## Operational invariants

- One bot-managed Antigravity session and one active agent job per project. Concurrent input ingestion does not authorize concurrent turns. From phase two, ownership must also cover project/profile/conversation identity, not just one database path; polling ownership is by bot ID. Enforce this across restarts and handle surviving children. Do not claim detection of a competing manually opened conversation without a verified CLI capability.
- Persist incoming updates before acknowledging them. Acknowledge only durable input; the default polling handler lifecycle alone is not a durability guarantee.
- The unread cursor, Telegram tool requests, action attempts and outcomes are durable. Persist a claimed attempt before network submission so a crash cannot reset a possibly sent operation to a safe pending state. Never hold a database transaction while awaiting the model, network or a human response. Do not share an AsyncSession between concurrent tasks.
- Revalidate actor permissions, target and draft/request revision immediately before an external action. Cancellation cannot undo an already submitted operation.
- Reconcile unknown external outcomes before retrying. Retrying a Telegram notification must not repeat a GitHub mutation. Do not claim exactly-once external delivery.
- Preserve message edits, speaker identity, reply/topic links, decision provenance and superseded decisions. Summaries do not replace source evidence.
- When implementing the second milestone, bind reviews to base/head SHAs and recheck before publishing. Review snapshots must not switch the user's working branch.
- Telegram tools may execute while the turn is active; their external effects survive turn failure or cancellation. Do not defer all communication until turn success, repeat the whole prompt to retry a notification, or auto-publish ordinary session text. Validate the active turn/generation for new calls, fixed project/topic and message reference; retries reuse a durable request ID and prior outcomes remain readable. Accepted pending requests may continue after turn success if still current; cancel unsent requests on turn failure/cancellation and retain potentially submitted attempts as unknown. Return actual sent/pending/unknown/rejected outcomes and preserve per-message reaction ordering and RetryAfter deadlines.
- Bot-provided GitHub issue creation still uses prepare and submit in the parent process. Its submit becomes runnable only after a successful turn; queued/staged is not success. Persist actual results as internal events for the same session, allowing a later turn to choose Telegram communication. Keep the adapter's dedicated credentials in the parent, never in agent arguments/environment or MCP configuration. Ordinary native tool authentication is not disabled by this rule. Reconcile unknown outcomes before retrying.
- When a project change needs a git commit, the agent commits it in that same turn with its own git in the project root. This is not a database commit and not a push. Do not add an approval button for it. Never commit secrets or `.env`. If the commit result is unknown, read the repository before creating another commit.
- `/screen` is the admin's private-chat view of the one Antigravity session and the process around it. The group topic does not receive that view. The picture is built from the ACP session the bot holds. It shows the turn, plan, recent tool steps, in-progress text, model, mode, tool permission, and whether the session is working, idle, or stopped. Refresh updates that same view. Also show lock ownership, whether the saved conversation is loaded, the last error without the token, unread count, last save time and Telegram tool outcomes, including reaction-only/silent turns and pending/unknown sends. From phase four, show unknown GitHub actions and the latest actual issue link. Do not invent a second session or a session list.

## Code quality and validation

- Use type annotations for interfaces and application code; validate untrusted payloads at boundaries. Keep domain rules explicit, names descriptive and error handling specific.
- Target Ruff lint/format and strict mypy. Suppressions must be narrow and explained. Document contracts, invariants and non-obvious decisions; avoid comments that repeat code.
- Use the installed `python-design-patterns`, `python-code-style`, `async-python-patterns` and `python-testing-patterns` skills when their workflows apply. Read relevant references on demand; examples are guidance, not automatically correct project code.
- Keep async I/O nonblocking, bound background work and retries, propagate cancellation after cleanup, and close subprocesses/connections on shutdown. A semaphore limits concurrency, not requests per time interval.
- Test meaningful behavior: queue exclusivity, durable ACK, crash recovery, stale drafts/grants, cancellation, reaction-only and silent turns, unknown API outcomes, and stale reviews when implementing the second milestone. Prefer fakes at external boundaries and real temporary SQLite files for persistence tests. Keep routine tests offline.
- After the development environment exists, run `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy src/peyda_pm_bot` and relevant `uv run pytest` checks. Report actual check results; offline success is not live service validation.
- Keep secrets, private chat exports, local databases, logs and authentication state out of commits and fixtures. Use sanitized examples and `.env.example` with placeholders when configuration is implemented.
- Update the plan and relevant product documentation when implementation establishes a new decision. Keep changes scoped to the current deliverable.
- Before a coding change, identify its owning module, existing implementation path, public contract, failure cases and acceptance criterion. Deliver a small end-to-end behavior with relevant checks. Add executable import-boundary checks when the source tree is created; do not weaken them merely to accommodate generated code. Record substantive architecture changes with rationale and update the canonical docs together.

## Telegram features and verified aiogram APIs

- Modern Telegram Bot API features may be used when they improve the current management-bot flow. Start with `docs/TELEGRAM_BOT_API_REFERENCE.md`; new features do not expand product scope or move PR review into the first milestone.
- Before implementing or changing a Telegram feature, check the official Telegram changelog/method documentation and the matching aiogram documentation for the installed/locked version. Confirm the actual Python method, model fields, required permissions and supported chat type. Do not translate a camelCase API name into an assumed Python API or infer availability from another SDK.
- The recorded baseline is aiogram 3.32.0 with Bot API 10.4 support, checked on 2026-11-17. It is a dated reference, not a perpetual claim about the latest release. Check PyPI for the current stable version when establishing/upgrading dependencies, then lock the chosen compatible version in `uv.lock`. Do not call it installed before installation or use moving `/latest/` documentation as proof about an older locked package.
- For each adopted new feature, update the reference with the Telegram and aiogram links, checked versions/date, exact method/fields and restrictions. If sources conflict or cannot be retrieved, state what remains unverified; do not invent a signature or silently assume support. Inspect the installed package or the official versioned distribution when needed.
- Distinguish Bot API from MTProto, guest/managed bots from this group's member bot, private-chat drafts/widgets from group-topic messages, and business checklists from ordinary bot messages. A Telegram tag, Premium status or a visual button state does not grant an application role or approve an action.
- Keep optional UI enhancements behind a verified capability decision and a simple supported fallback. In the `pm` group topic, use persisted messages and bounded edits when private-chat-only streaming is unavailable; never report a temporary draft or ephemeral message as a durable team notification.
- Test new payloads and policy behavior offline during development. The user has authorized early live checks; distinguish each verified adapter/tool from the remaining final integration acceptance.

## Memory policy agreed with the user

The managed team consists of three peers; do not invent a product-manager role. Asking about ambiguous decisions, confirming removal, notifying recorded changes and seeking at least two confirmations for sensitive decisions are agent prompt instructions. A bot reaction is not a human approval. Do not add vote-counting, sensitivity classification or approval gates in code for these rules. Technical project/source/revision/turn validation remains mandatory. Memory tools only stage changes; the active worker atomically commits them with the successful job and durable result events. A later turn may communicate the confirmed result through Telegram tools; never announce staged changes as committed. Preserve history and evidence. Draft architecture text stays in the bot database; the memory API never writes the managed repository. This does not constrain Antigravity's native file tools.

## GitHub policy agreed with the user

A finished project change is committed with agy's own git when that commit is the record the work needs. Consensus and sensitive-operation confirmation remain agent prompt rules for GitHub too; do not add approval buttons, vote counting or a mandatory human-approval table. For bot-provided GitHub tools, prepare and submit are distinct operations; submission becomes runnable only after a successful turn. Validate repository binding, source freshness, draft revision and allowed operation types in code. Keep the adapter's dedicated credentials in the main process, never in agent arguments/environment or MCP configuration. Native git/gh remain available under their ordinary profile settings; do not misrepresent native operations as protected by the bot executor. Unknown outcomes are reconciled, never blindly resent. Preserve external race and incomplete-pagination limitations in reports.
