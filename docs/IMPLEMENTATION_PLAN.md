# پلن پیاده‌سازی Peyda PM Bot

تاریخ: ۲۰۲۶-۱۱-۱۷.

به‌روزرسانی ۲۰۲۶-۱۱-۲۱: از فاز یک، هر برشی که به تلگرام، Antigravity یا گیت‌هاب می‌رسد روی همان سرویس واقعی هم امتحان می‌شود. تست آفلاین جای این امتحان را نمی‌گیرد. فاز شش پذیرش یکپارچه است، نه اولین‌بار وصل‌شدن.

بازنگری قرارداد: ساخت از ابتدا با Antigravity عادی و ابزارهای افزودهٔ بات. ایجنت در همان نوبت می‌تواند پیام/reply بفرستد، فقط ری‌اکشن بزند یا ساکت بماند. متن جلسه خودکار کپی نمی‌شود و تعداد خروجی به یک جواب محدود نیست. مرز دقیق و دلیل این تصمیم در بخش‌های ۹ تا ۱۳ [معماری](ARCHITECTURE.md) است.

این سند پلن اجرایی [README](../README.md) است. تصمیم‌های قطعی محصول در README مرجع‌اند؛ انتخاب‌های فنی زیر برای اجرای نسخه اول پیشنهاد می‌شوند و در شروع هر فاز با نتیجه آزمایش تطبیق داده می‌شوند. قرارداد تفصیلی مرز ماژول‌ها، تراکنش‌ها و توسعه در [ARCHITECTURE.md](ARCHITECTURE.md) آمده است.

## ۱. نقطه شروع و محدوده

تحویل محصول دو مرحله مستقل دارد: **ابتدا بات مدیریت پروژه**، سپس **افزودن ریویو PR**. تست واقعی بات مدیریت از اولین فاز شروع می‌شود و منتظر ریویو یا فاز شش نمی‌ماند.

- پیاده‌سازی از صفر با Python و aiogram 3؛ `tele-agy` فقط مرجع اتصال و رفتار ACP است.
- اجرای محلی روی لپ‌تاپ: یک پروژه، یک گروه مجاز، یک نشست Antigravity و حداکثر یک کار فعال ایجنت.
- بات به گروه و تاپیک `pm` متصل شده و دریافت پیام معمولی در فاز یک ثبت شده است. binding عددی محلی در تنظیمات است؛ نام تاپیک کلید هویت نیست و شناسهٔ ناشناس خودکار مجاز نمی‌شود.
- تلگرام وب در Brave برای تست رابط در دسترس است؛ آزمون‌های خودکار به آن یا حساب شخصی وابسته نمی‌شوند.
- محیط مجازی و lockfile موجودند: Python 3.14.4 و aiogram 3.32.0؛ `uv` در `.venv/bin/uv` است و الزاماً در PATH عمومی نیست.
- مسیر `~/.local/bin/agy-cli` موجود است؛ لانچر GUI عوض نشده. وجود binary اثبات ورود، load، ابزار یا اجرای واقعی ACP نیست؛ این موارد هنوز تحویل فاز دو هستند.
- سرور عمومی، داشبورد، Mini App، مرج خودکار و دیپلوی خودکار در نسخه اول برنامه‌ریزی نمی‌شوند.

ترتیب اجرا: هر فاز اول رفتار و خرابی را با تست آفلاین ثابت می‌کند، و همان فاز روی سرویس واقعی هم دیده می‌شود. نصب CLI، ورود و شناسهٔ گروه و تاپیک مال شروع کارند. توسعه ریویو PR بعد از تحویل بات مدیریت و در مرحلهٔ جدا انجام می‌شود. pytest به `.env` و حساب واقعی وصل نمی‌شود. تست زنده فرمان جداست.

اولین تحویل: یک پیام واقعی تاپیک ذخیره شود، به تلگرام ACK داده شود، و بعد از ری‌استارت دوباره پردازش نشود. جواب ایجنت از فاز دو روی همان تاپیک بررسی می‌شود.

وضعیت کد فعلی در بازنگری ۲۰۲۶-۱۱-۲۱: دریافت پایدار، نسخهٔ پیام، checkpoint، `/health` و قفل هر دیتابیس ساخته شده‌اند؛ ۳۸ تست آفلاین و یک دریافت زنده در [گزارش تست](LIVE_TESTING.md) ثبت‌اند. اتصال ACP، ابزارهای تلگرام و قابلیت‌های فازهای بعد هنوز ساخته نشده‌اند. برای بستن فاز یک، نگاشت عددی `edit_date`، crash بین ارسال `/health` و ثبت نتیجه، رعایت زمان RetryAfter و ثبت روشن سناریوی ری‌استارت زنده باید رسیدگی شوند؛ بازپخش محلی جای مشاهدهٔ مستقل ری‌استارت واقعی نیست.

## ۲. اسکیل‌های انتخاب‌شده

چهار اسکیل از مخزن اصلی [wshobson/agents](https://github.com/wshobson/agents/tree/9c61ab243def98f72da12abd41cfcf5bcd91af9d/plugins/python-development/skills) بررسی و در `~/.codex/skills` نصب شدند. این‌ها راهنمای توسعه Codex هستند، نه وابستگی اجرایی بات یا اسکیل نصب‌شده در Antigravity.

| اسکیل | کاربرد در پروژه |

| `python-design-patterns` | تفکیک منطق محصول از I/O، ترکیب اجزا و پرهیز از abstraction زودهنگام |

| `async-python-patterns` | چرخه عمر taskها، subprocess، timeout، cancellation و دریافت غیرمسدودکننده |
| `python-testing-patterns` | pytest، fake برای سرویس‌های بیرونی و آزمون بازیابی و خطا |

نسخه منبع برای هر چهار اسکیل: `9c61ab243def98f72da12abd41cfcf5bcd91af9d`؛ مسیر هرکدام `plugins/python-development/skills/<name>` است. نصب اسکیل به معنی تضمین صحت نمونه‌کدهای آن نیست؛ مثال‌ها باید با نیاز پروژه و مستندات کتابخانه تطبیق داده شوند. مثلاً چند consumer برای ایجنت مجاز نیست و semaphore به‌تنهایی کنترل نرخ زمانی محسوب نمی‌شود.

## ۳. معماری پیشنهادی

یک برنامه ماژولار در یک پردازش، با مرز روشن بین قواعد محصول و اتصال‌های بیرونی. هر فاز فقط ماژول‌های موردنیاز همان تحویل را اضافه می‌کند.

تقسیم قابلیت‌ها درون هر لایه انجام می‌شود: `conversations`، `memory`، `work` و `actions`؛ `reviews` فقط در مرحله دوم. هر قابلیت صاحب قواعد و داده خود است؛ ارتباط بین قابلیت‌ها از API عمومی application و DTOهای typed انجام می‌شود. ساختار زیر نمای لایه‌هاست، نه مجوز ایجاد فایل‌های بزرگ و همه‌منظوره برای هر لایه.

```text
Telegram getUpdates
        |
  ذخیره پایدار، بعد ACK
        |
  خط‌های نخوانده در یک session/prompt
        |
  یک نشست Antigravity
        |
  ابزار تلگرام در همان نوبت: پیام / reply / ری‌اکشن / سکوت
```

دریافت ورودی، ارسال خروجی و تطبیق گیت‌هاب می‌توانند هنگام اجرای ایجنت فعال بمانند. صف ایجنت یک مصرف‌کننده دارد؛ این محدودیت در برنامه و تست اعمال می‌شود. در مرحله اول، خواندن وضعیت و پیوند PR برای هماهنگی تیم مجاز است؛ تحلیل diff، تولید یافته فنی و انتشار review به مرحله دوم تعلق دارند. ماژول، جدول و زمان‌بندی اختصاصی ریویو هنگام افزودن همان قابلیت ایجاد می‌شوند.

ساختار مقصد:

```text
src/peyda_pm_bot/
  __main__.py              # entry point
  bootstrap.py             # ساخت وابستگی‌ها و چرخه عمر برنامه
  config.py                # تنظیمات معتبر و بدون اسرار در خروجی
  domain/                  # مدل‌ها، قواعد نقش و انتقال وضعیت
  application/             # use caseها، هماهنگی صف، حافظه و اقدام‌ها
    ports.py               # Protocolهای کوچک فقط در مرزهای I/O
  adapters/
    telegram/              # polling، نرمال‌سازی، router و ارسال
    antigravity/           # ACP، رویدادها، permission و بازیابی نشست
    github/                # API، polling، تطبیق و snapshot
    storage/               # مدل‌های SQLAlchemy و repositoryها
    tools/                 # ابزارهای افزودهٔ تلگرام، حافظه و اقدام، هنگام نیاز واقعی
  runtime/                 # قفل پردازش، worker، زمان‌بندی و shutdown
migrations/
tests/{unit,integration,acceptance}/
docs/
```

جهت وابستگی: `application` به `domain` و قراردادهای I/O وابسته است؛ adapterها این قراردادها را پیاده می‌کنند. فقط `bootstrap` پیاده‌سازی‌های واقعی را به هم وصل می‌کند. مدل aiogram، ORM و JSON-RPC به قواعد دامنه نشت نمی‌کنند. بین ماژول‌ها handler دیگری را صدا نمی‌زنیم.

الگوهای مورد استفاده، با دلیل:

- **Ports & Adapters در مرز I/O:** تعویض ارتباط واقعی با fake بدون اجرای تلگرام یا مدل در تست.
- **Dependency Injection دستی:** انتقال وابستگی‌ها در سازنده یا پارامتر؛ بدون framework تزریق وابستگی.
- **Repository و تراکنش کوتاه:** جداکردن SQL و اتمیک‌کردن تغییرات مرتبط؛ بدون repository عمومی برای همه جدول‌ها.
- **Unit of Work سبک:** کنترل تراکنش از use case برای تغییر چند repository؛ commit در repository انجام نمی‌شود و عملیات شبکه خارج تراکنش باقی می‌ماند.
- **Inbox / Outbox:** ورودی پایدار پیش از تأیید دریافت؛ ارسال اعلان جدا از اجرای عملیات اصلی.
- **State Machine صریح:** انتقال‌های معتبر کار و اقدام (و ریویو در مرحله دوم)؛ تابع و enum کافی است، مگر پیچیدگی واقعی خلافش را ثابت کند.

برای هر کلاس، لایه یا الگوی جدید باید مسئله مشخصی وجود داشته باشد. microservice، Redis، Celery، event sourcing کامل و framework عمومی workflow برای نسخه اول لازم نیستند.

## ۴. ابزارهای توسعه و ذخیره‌سازی

| بخش | انتخاب پیشنهادی |
|---|---|
| Python | حداقل 3.12؛ نسخه محیط محلی پس از بررسی سازگاری وابستگی‌ها قفل می‌شود |
| وابستگی و محیط | `uv`، `pyproject.toml` و `uv.lock` |
| تلگرام | `aiogram 3`؛ نسخه دقیق هنگام ساخت lockfile |
| دیتابیس | SQLite محلی با WAL، foreign keys و busy timeout |
| دسترسی به داده | SQLAlchemy async با `aiosqlite`؛ `AsyncSession` جدا برای هر واحد کار |
| migration | Alembic؛ هر تغییر schema همراه migration قابل آزمایش |
| تنظیمات و ورودی ابزار | Pydantic و تنظیمات محیطی معتبر؛ اسرار خارج مخزن |
| کیفیت | Ruff برای lint/format و mypy strict برای کد برنامه |
| تست | pytest و pytest-asyncio؛ دیتابیس موقت و ساعت قابل تزریق |
| لاگ | logging ساخت‌یافته با شناسه کار/رویداد و حذف اسرار و متن خصوصی غیرضروری |

aiogram 3.32.0 در محیط فعلی نصب و در lockfile قفل است. نسخهٔ مرجع Bot API در بررسی مستند ۲۰۲۶-۱۱-۲۱، 10.4 است؛ این ادعای آخرین نسخهٔ همیشگی نیست. هنگام ارتقا انتشار پایدار و سازگاری دوباره بررسی می‌شوند. برای نام/پارامتر دقیق و محدودیت واقعی سرویس، [مرجع Telegram و aiogram](TELEGRAM_BOT_API_REFERENCE.md) و قوانین AGENTS.md مبنا هستند؛ وجود متد در SDK تست زنده نیست.

وضعیت صف، زمان تجمیع پیام‌ها و offset ورودی در دیتابیس است؛ `asyncio.Queue` تنها می‌تواند نقش بیدارکردن worker را داشته باشد. هیچ تراکنشی هنگام انتظار برای مدل، شبکه یا تأیید انسانی باز نمی‌ماند. ORM session بین taskها مشترک نیست.

گروه داده‌ها به‌تدریج ایجاد می‌شوند: تنظیم پروژه و نقش‌ها؛ inbox و نسخه پیام‌ها؛ بسته‌ها و jobs؛ نشست و checkpoint؛ درخواست و تلاش ابزار تلگرام و outbox؛ پرونده و شواهد؛ draft و submit و نتیجهٔ اقدامات گیت‌هاب؛ وضعیت تطبیق ایشو/PR. schema یا جدول رأی‌شماری و تأیید انسانی اجباری نداریم. داده‌های اختصاصی ریویو در مرحله دوم اضافه می‌شوند. کلیدهای یکتا و روابط لازم از اولین migration مرتبط تعریف می‌شوند.

## ۵. قراردادهای پایداری و اختیار

1. قفل فعلی هر دیتابیس برای دریافت فاز یک است. فاز دو علاوه بر آن، مالکیت پروژه/پروفایل/گفت‌وگو و polling بر اساس bot ID را کنترل می‌کند تا مسیر دادهٔ دوم قفل را دور نزند. worker تنها صاحب subprocess نشست بات است؛ قبل از جایگزینی، توقف child قبلی تأیید می‌شود. کار همزمان دستی روی همان گفت‌وگو تا اثبات قفل مشترک CLI یک محدودیت عملیاتی است، نه قابلیت کشف‌شدهٔ برنامه.
2. `getUpdates` در حلقه ورودی کوتاه اجرا می‌شود؛ updateها و offset بعدی در یک تراکنش ثبت می‌شوند، سپس درخواست تأییدکننده بعدی ارسال می‌شود. تکیه بر handlerهای پس‌زمینه پیش‌فرض برای تضمین ذخیره پیش از ACK کافی نیست. بعداً dispatcher از inbox تغذیه می‌شود. شکست ذخیره به معنی پیش‌نبردن offset است.
3. `update_id` تکراری اثر دوباره ندارد؛ ویرایش پیام نسخه جدید همان پیام است. دریافت ورودی و تکرار پردازش دو مفهوم جدا هستند.
4. خط‌های نخوانده یک `session/prompt` هستند؛ یک نوبت الزام به یک خروجی ندارد. مکث کوتاه فقط برای ورودی تازه است و backlog قدیمی مکث اضافه ندارد. نام، هویت و ارجاع پایدار گوینده/پیام، نسخه و reply همراه متن می‌مانند. اگر backlog از ظرفیت واقعی prompt بیشتر شد، برنامه بی‌صدا آن را truncate یا به چند نوبت خودکار تقسیم نمی‌کند؛ تصمیم ظرفیت در فاز دو ثبت می‌شود.
5. لغو و اصلاح صریح، نسخه درخواست و اقدام‌های وابسته را فوراً در لایه برنامه نامعتبر می‌کنند؛ تشخیص معنایی در نوبت ایجنت است. اقدام در انتظار تصمیم مبهم، پیش از رفع ابهام اجرا نمی‌شود.
6. ابزارهای افزوده actor، مقصد، نوبت/generation و نسخهٔ دقیق درخواست یا draft را پیش از ارسال دوباره بررسی می‌کنند. توافق انسانی و حساسیت تصمیم دستور ایجنت است، نه approval engine. مجوز عادی ابزارهای agy حفظ می‌شود و خودکار تأیید یا محدودتر نمی‌شود.
7. چرخهٔ درخواست ابزار `pending → executing → succeeded` با مسیرهای `cancelled / stale / rejected / unknown` است؛ draft و staged فقط برای عملیات نیازمند آن‌ها اضافه می‌شوند. تلاش پیش از شبکه durable است. ابزار تلگرام در نوبت فعال فراخوانی و قابل اجراست؛ درخواست معتبر pending پس از موفقیت نوبت هم با کنترل تازگی/لغو می‌تواند ادامه یابد، ولی شکست یا لغو نوبت ارسال‌نشده‌ها را لغو می‌کند. حافظه و submit ابزار GitHub تا پایان موفق staged می‌مانند. شکست ارسال، نوبت یا عملیات موفق را تکرار نمی‌کند.
8. عملیات گیت‌هاب با نتیجه نامعلوم پیش از retry تطبیق داده می‌شود. برای ساخت ایشو، شناسه پایدار اقدام در بدنه/metadata قابل جست‌وجو قرار می‌گیرد. برای تلگرام هم وضعیت نامعلوم ارسال جدا ثبت می‌شود؛ تضمین exactly-once نمی‌دهیم.
9. پیام گروه، متن PR و کد منبع نمی‌توانند binding و مجوز APIهای بات را تغییر دهند. این کنترل، sandbox همهٔ ابزارهای عادی Antigravity یا تضمین جلوگیری از prompt injection نیست؛ shell و `gh` عادی از executor بات عبور نمی‌کنند.
10. توکن اختصاصی بات و متغیرهای `PEYDA_*` به محیط/آرگومان/تنظیمات ابزار agy داده نمی‌شوند. مدل، حالت، سطح اجازه، ابزار فایل/ترمینال/git و ورود معمول پروفایل حفظ می‌شوند. cwd پروژه sandbox جدید نیست. انتشار گروه فقط با ابزار تلگرام است؛ متن جلسه خودکار کپی نمی‌شود. تغییر نیازمند کامیت در همان نوبت و با git خود agy کامیت می‌شود؛ push عمل جداست.
11. حافظه نسخه‌دار و مستند به پیام است. خلاصه با محدوده پوشش و منبع نگهداری می‌شود؛ تصمیم جایگزین‌شده حذف نمی‌شود. اصلاح پیوند پرونده یا تصمیم، پردازش‌های وابسته را برای بازبینی علامت می‌زند.
12. در مرحله دوم محصول، ریویو به `(repository, PR, base SHA, head SHA)` و checkpoint مرحله تعلق دارد. قبل از انتشار، نسخه دوباره تطبیق داده می‌شود.
13. سکوت و ری‌اکشن تنها پایان معتبرند و cursor نوبت موفق را جلو می‌برند. ثبت درخواست محلی یا submit staged موفقیت سرویس نیست. نتیجهٔ قطعی حافظه/ایشو رویداد داخلی همان نشست است و در صورت نیاز در نوبت بعد با ابزار تلگرام اعلام می‌شود؛ متن موفقیت زودهنگام تولید نمی‌شود.
14. ACK دریافت، پیش‌بردن offset پروتکل است؛ برنامه برای هر پیام ری‌اکشن یا پاسخ رسید خودکار نمی‌فرستد. ارتباط تیم انتخاب ایجنت است.

## ۶. مرحله اول محصول — بات مدیریت پروژه

هر فاز تست آفلاین دارد تا قطع شبکه، تکرار و ری‌استارت بدون سرویس بیرونی تکرار شوند. همان فاز یک چک واقعی هم دارد. موفقیت fake به‌معنای کارکرد تلگرام، ACP یا گیت‌هاب نیست و در گزارش از نتیجهٔ زنده جدا نوشته می‌شود.

### فاز یک — اسکلت و ذخیره مطمئن تلگرام

- محیط مجازی، ابزارهای کیفیت، تنظیمات، bootstrap و migration اولیه.
- تعیین owner و قرارداد هر قابلیت طبق ARCHITECTURE.md؛ بررسی خودکار مرز importها و lifecycle بدون اثر جانبی هنگام import. ابتدا آزمون rollback و ثبت اتمیک inbox/checkpoint با دیتابیس موقت، سپس مسیر دریافت پیام ساخته شود.
- allowlist گروه/تاپیک و مدیر، دریافت پایدار پیام و ویرایش، شناسه گوینده، reply، topic و ترتیب ورودی.
- نصب CLI در کنار GUI، بدون جایگزینی لانچر فعلی، و ثبت مسیر binary. کشف شناسهٔ واقعی گروه، تاپیک `pm` و مدیر، و بررسی Privacy Mode. شناسه و نقش ناشناس به‌صورت خودکار مجاز نمی‌شوند.
- پاسخ محلی ساده برای سلامت سرویس. این جواب مدل نیست.

**تحویل آفلاین:** crash بین دریافت و ACK پیام را گم نکند و update تکراری رکورد تازه نسازد. پیام خارج محدوده وارد پردازش محصول نشود.

**تحویل زنده:** یک پیام واقعی در تاپیک `pm` ذخیره شود و فقط بعد از ذخیره ACK بگیرد. ری‌استارت همان پیام را دوباره پردازش نکند.

### فاز دو — صف و قرارداد مکالمه تک‌نشستی

- بسته‌بندی پایدار پیام‌ها، صف و بازیابی کار ناتمام، timeout و retry محدود با backoff.
- یک agent worker با مالکیت پروژه/گفت‌وگو و polling، مدیریت subprocess و shutdown؛ ذخیره session ID و checkpoint و بازیابی child باقی‌مانده.
- اتصال ACP به CLI نصب‌شده و بازکردن گفت‌وگوی ذخیره‌شده. fake agent فقط سناریوی خرابی و قفل تک‌نوبتی را تکرار می‌کند. دستور ثابت گفت‌وگو شامل این است که تغییر لازم، در همان نوبت کامیت گیت شود.
- مقایسه با اجرای مستقیم همان پروفایل: ابزارهای داخلی فایل/ترمینال/git، مدل، حالت و سطح اجازه حفظ شوند. تست ساخت و ویرایش فایل آزمایشی با ابزار خود agy؛ wrapper فایل، منع بازنویسی یا sandbox تازه اضافه نشود. credential اختصاصی بات در والد بماند و ابزارهای عادی پروفایل دستکاری نشوند.
- ابزار تلگرام برای پیام، reply به ارجاع مشخص و تنظیم/تعویض/برداشتن ری‌اکشن خود بات. ابزار در میانهٔ همان نوبت قابل اجراست؛ پروژه/تاپیک و نوبت فعال در والد اعتبارسنجی می‌شوند. schema و transport احرازشده با نسخهٔ واقعی ACP تأیید شوند.
- درخواست/تلاش ارسال و نتیجهٔ پیام یا ری‌اکشن durable باشند و مشاهدهٔ وضعیت درخواست قبلی ممکن باشد. تکرار همان tool call خروجی دوباره نسازد؛ چند پیام عمدی ایجنت مجازند. ادامهٔ pending بعد از موفقیت نوبت، لغو ارسال‌نشده‌ها پس از شکست، ترتیب ری‌اکشن، RetryAfter و deadline پایدار و crash پس از ارسال پوشش داده شوند. نتیجهٔ unknown پیام دوباره ارسال نشود.
- ثبت ورودی جدید هنگام پاسخ طولانی، بدون شروع نوبت دوم. بعد از پایان نوبت، خط‌های جدید یک پرامپت می‌شوند. ارجاع پیام/نسخه و گوینده برای انتخاب reply/ری‌اکشن روشن باشد؛ متن جلسه خودکار به گروه نرود.
- انتخاب پیام، چند پیام لازم، فقط ری‌اکشن یا سکوت با ایجنت است؛ برای پایان نوبت، ردشدن ری‌اکشن یا نبود متن، پیام جایگزین نسازیم. پایان موفق بدون متن هم cursor را جلو ببرد؛ اثرهای ارتباطی نوبت ناموفق حفظ شوند و whole-turn retry صرفاً به‌دلیل شکست ارسال انجام نشود.
- `/screen` در چت خصوصی مدیر. تصویر از نشست ACP ساخته می‌شود و تاپیک گروه آن را نمی‌گیرد. بخش‌ها: صفحهٔ Antigravity، وضعیت برنامه، و صف تلگرام. تازه‌سازی همان نما را وسط کار عوض می‌کند. بخش گیت‌هاب در فاز چهار به همین نما اضافه می‌شود.
- انتخاب کارها با زمان انتظار برای گفتگو، ثبت تصمیم و درخواست‌های مدیریت؛ سیاست اولیه قابل تنظیم و تست جلوگیری از گرسنگی صف. زمان‌بندی ریویو در مرحله دوم اضافه می‌شود.

**تحویل آفلاین:** با دو گوینده فقط یک نوبت فعال بماند؛ ری‌اکشن تنها/سکوت هیچ پیام اجباری نسازند، حتی اگر متن ترمینال وجود داشته باشد. تکرار call، مقصد اشتباه، grant منقضی، reply ناموجود، ترتیب ری‌اکشن، crash ارسال و unknown پوشش داده شوند. نشست بعد از ری‌استارت همان گفت‌وگو را باز کند و مسیر دیتابیس دوم قفل نشست را دور نزند.

**تحویل زنده:** چند خط واقعی تاپیک یک `session/prompt` شوند. در اجرای واقعی، پیام/reply وسط نوبت، فقط ری‌اکشن بدون متن اضافه، تعویض/برداشتن آن و سکوت دیده شوند. متن معمول پایان نوبت پیام تکراری نسازد. ابزارهای عادی agy مثل اجرای مستقیم کار کنند و permission واقعی حفظ شود. پیام وسط کار نوبت همزمان نسازد. `/screen` در چت خصوصی مدیر همان نوبت و نتیجهٔ ابزار تلگرام را نشان دهد. آزمون چندنفره تا حضور عضو دوم تأییدشده اعلام نشود.

### فاز سه — پرونده و حافظه مستند

سیاست توافق و موارد حساس فقط در متن ایجنت است.

- ابزارهای افزودهٔ جست‌وجو، خواندن و به‌روزرسانی پرونده با کنترل پروژه و schema ورودی؛ این محدودهٔ API حافظه است و ابزارهای عادی agy را محدود نمی‌کند.
- ارتباط چندبه‌چند پیام/پرونده؛ تفکیک پیشنهاد، تصمیم، تعهد و برداشت؛ نسخه‌بندی و منبع.
- جست‌وجوی متنی و alias برای شروع؛ ارزیابی FTS با متن فارسی پیش از استفاده. دیتابیس برداری فقط در صورت ضعف قابل اندازه‌گیری جست‌وجو بررسی می‌شود.
- خلاصه‌های تدریجی با بودجه زمینه و شواهد اصلی؛ ابزار اصلاح پیوند نادرست و تصمیم قبلی.
- تهیه متن پیشنهادی تصمیم معماری در حافظه؛ API حافظه فقط دیتابیس بات را تغییر می‌دهد و فایل مخزن نمی‌نویسد. این مرز، اختیار ابزارهای عادی فایل agy را تغییر نمی‌دهد.
- پاسخ staged با ثبت قطعی فرق داشته باشد. commit موفق، نتیجه‌ای پایدار برای همان نشست بسازد تا ایجنت در صورت نیاز در نوبت بعد از ابزار تلگرام استفاده کند؛ پیام موفقیت اجباری یا زودهنگام نداریم. ابزار حافظه مجوز نوشتن فایل ایجاد نمی‌کند؛ ابزارهای عادی agy طبق درخواست کاربر و تنظیمات خودش باقی می‌مانند.

**تحویل آفلاین:** بعد از تغییر موضوع و ری‌استارت، ابزار حافظه تصمیم قبلی را با منبع برگرداند.

**تحویل زنده:** در همان نشست، برگشتن به موضوع قبلی تصمیم مستند را برگرداند و ایجنت در صورت نیاز آن را با ابزار پیام اعلام کند. لغو نوبت، ثبت staged را قطعی یا موفق اعلام نکند.

### فاز چهار — ساخت ایشو و هماهنگی شروع کار

توافق و تأیید تیم یک‌بار در گفت‌وگوی ذخیره‌شده است. submit نسخهٔ مشخص را در کد کنترل می‌کند.

- اتصال گیت‌هاب برای خواندن و ساخت ایشو. fake transport سناریوی جواب گم‌شده را تکرار می‌کند. حساب واقعی در همین فاز یک ایشو آزمایشی می‌سازد.
- پیش‌نویس شامل محدوده، معیار پایان، مسئول پیشنهادی و وابستگی؛ پیش‌نویس و submit نسخه‌دار. توافق انسانی در متن گفت‌وگوی ذخیره‌شده است و approval engine ندارد.
- executor مستقل برای ساخت/تکمیل ایشو، ثبت تلاش و تطبیق نتیجه نامعلوم. submit فقط staged/queued است؛ بعد از موفقیت نوبت اجرا می‌شود و نتیجهٔ واقعی به‌صورت رویداد داخلی در نوبت بعدی همان نشست دیده می‌شود. خبر گروه با ابزار تلگرام و تصمیم ایجنت است. بخش گیت‌هاب در `/screen` اقدام نامعلوم و آخرین لینک واقعی ایشو را نشان می‌دهد.
- API گیت‌هاب بات، ابزارهای داخلی مثل `gh` را نمی‌بندد. ضمانت binding/dedup/reconciliation مربوط به همان adapter است؛ عملیات بومی ترمینال با نتیجهٔ واقعی خودشان بررسی می‌شوند و زیر تضمین ساختگی بات قرار نمی‌گیرند.
- اعلام شروع، بررسی هم‌پوشانی، پیش‌نیاز و کار نیمه‌تمام؛ نگاشت اولیه وضعیت‌ها به labels با نام‌های قابل تنظیم، بدون اجبار GitHub Projects.

**تحویل آفلاین:** لغو پیش از اجرا و submit پیش‌نویس قدیمی رد شوند. گم‌شدن پاسخ ساخت ایشو باعث ساخت دوباره نشود. نتیجهٔ queued موفقیت ساخت تلقی نشود و شکست خبر تلگرام، ایشو را تکرار نکند.

**تحویل زنده:** یک ایشو آزمایشی از مسیر `prepare` و `submit` ساخته شود؛ پس از نتیجهٔ واقعی، ایجنت در نوبت بعدی همان نشست لینک را با ابزار تلگرام بفرستد. نشست دوم ساخته نشود.

### فاز پنج — پیگیری و آماده‌سازی استفاده روزمره

- گزارش درخواستی، مانع و اقدام بعدی؛ یادآوری با زمان‌بندی قابل تنظیم، dedup و جلوگیری از اعلان بدون تغییر.
- یادآوری یک ورودی پایدار همان نشست است؛ انتخاب متن، ری‌اکشن یا سکوت همچنان با ایجنت است. ارسال موفق، خاموش‌بودن آگاهانه و ارسال نامعلوم در وضعیت scheduler از هم جدا باشند تا یک موعد بارها همان prompt را نسازد.
- تطبیق دوره‌ای گیت‌هاب، بررسی محافظت main و مستندسازی تنظیمات لازم؛ تغییر قواعد مخزن عملیات جدا و با اختیار مشخص است.
- بکاپ سازگار SQLite و آزمون restore، سیاست نگهداری/حذف پیام و پیوست، راهنمای نصب و رفع قطعی ورود.
- آماده‌کردن اجرای سرویس محلی با restart کنترل‌شده، ابزار اندازه‌گیری منابع و سناریوهای sleep/wake و قطع اینترنت برای پذیرش نهایی.

**تحویل آفلاین:** بکاپ و restore، و تکرارنشدن یادآوری بدون تغییر، روی SQLite موقت ثابت شوند. مرج همچنان انسانی است.

**تحویل زنده:** درخواست گزارش در تاپیک یک خط چت باشد و ایجنت از همان نشست با ابزار پیام گزارش بدهد. یک یادآوری بدون تغییر هم خروجی اجباری ایجاد نکند.

### فاز شش — پذیرش یکپارچه

اتصال واقعی از فاز یک شروع شده است. این فاز همان مسیر را یکجا و در استفادهٔ طولانی‌تر می‌سنجد.

- مرور نسخهٔ CLI، بارگذاری نشست، permission، لغو و خطای ورود روی همان گفت‌وگوی پروژه.
- اتصال و آزمون ابزارهای حافظه و آزمون مجوزهای عملیات اثرگذار. خواندن فایل با رفتار فعلی Antigravity پذیرفته شده و محدودسازی اضافهٔ خواندن از معیار تحویل خارج است.
- مرور یکسان‌بودن ابزارها و سطح اجازه با اجرای معمول پروفایل، که از فاز دو تست شده است. ساخت و ویرایش فایل و اجرای دستور از ابزارهای خود agy انجام شوند؛ این فاز wrapper فایل، منع بازنویسی یا sandbox تازه به ایجنت اضافه نکند.
- افزودن مسیر اجرای روزمره که دریافت تلگرام، نشست موجود Antigravity، همگام‌سازی GitHub، یادآوری و outbox را با هم راه بیندازد. مسیرهای تست اتصال کوتاه و مستقل از اجرای روزمره باشند.
- مرور دریافت پیام معمولی گروه و Privacy Mode، اگر از فاز یک چیزی جا مانده باشد.
- اجرای دوبارهٔ ساخت ایشو، لغو و تطبیق وضعیت در مخزن آزمایشی. انتشار review در این تحویل انجام نمی‌شود.
- تست سرتاسری در تلگرام: چند نفر، تغییر موضوع، بازیابی تصمیم، اصلاح درخواست، تغییر وضعیت تسک و ری‌استارت وسط جواب.
- پذیرش ارتباط مستقل: فقط ری‌اکشن، سکوت، چند پیام لازم در یک نوبت، ردشدن ری‌اکشن و متن پایانی ترمینال، بدون ارسال خودکار متن اضافه. شکست نوبت بعد از اثر بیرونی، اثر قبلی را پنهان یا تکرار نکند.
- تست sleep/wake لپ‌تاپ، قطع اینترنت و بازیابی؛ اندازه‌گیری RAM/CPU برنامه و Antigravity جداگانه و یک روز استفاده آزمایشی.

**تحویل:** نتیجهٔ سناریوهای README روی گروه واقعی، بازیابی بعد از sleep و قطع اینترنت، و فهرست صریح هر چیزی که هنوز زنده دیده نشده است. transcript خصوصی در مخزن نمی‌آید.

این مرحله پس از تحویل و تست واقعی بات مدیریت شروع می‌شود و شرط آماده‌شدن مرحله اول نیست. پلن مستقل در [PR_REVIEW_PLAN.md](PR_REVIEW_PLAN.md) آمده است. قابلیت ریویو به همان بات، همان ایجنت و همان نشست افزوده می‌شود؛ بات یا نشست دوم ساخته نمی‌شود.

## ۸. آزمون‌ها و معیار کیفیت

Unit test برای انتقال وضعیت، اعتبار نوبت/نسخه/مقصد، تجمیع و انتخاب صف. Integration test با SQLite فایل‌محور موقت برای migration، قفل، inbox/outbox و recovery؛ دیتابیس حافظه‌ای به‌تنهایی رفتار فایل و WAL را ثابت نمی‌کند. Adapterها با fake transport و رویداد واقعی پاک‌سازی‌شده آزمایش می‌شوند.

سناریوهای اجباری مرحله اول محصول؛ سناریوهای ریویو در پلن مستقل مرحله دوم آمده‌اند:

| سناریو | انتظار |
|---|---|
| crash پس از ذخیره inbox و پیش از ACK | بازپخش بدون اثر مضاعف |
| crash حین عملیات بیرونی | ثبت unknown و تطبیق پیش از retry |
| اجرای نمونه دوم با دیتابیس دیگر یا child قدیمی | جلوگیری از دو نشست/نوبت تحت مدیریت بات و دو poller همان bot |
| ویرایش/لغو حین انتظار | نامعتبرشدن نسخه قبلی و اقدام وابسته |
| درخواست ابزار با مقصد، grant یا revision قدیمی | رد پیش از شبکه و نتیجهٔ واقعی برای ایجنت |
| قطع نشست و ورود منقضی | حفظ صف و خطای قابل اقدام |
| بار پیوسته گفتگو و درخواست مدیریت | پیشرفت کارها بدون starvation |
| outbox ناموفق | retry فقط برای شکست مجاز، بدون تکرار prompt یا ساخت ایشو |
| ری‌اکشن تنها یا سکوت همراه متن ترمینال | هیچ پیام اجباری؛ پایان موفق و cursor پایدار |
| یک نوبت با چند پیام لازم | ترتیب و شناسهٔ مستقل اثرها، بدون کپی خودکار متن جلسه |
| crash بعد از ارسال و قبل از ثبت نتیجه | تلاش قبلی نامعلوم بماند و کورکورانه دوباره ارسال نشود |
| retry ری‌اکشن قدیمی بعد از درخواست تازه | پس‌نزدن وضعیت جدید با درخواست منقضی |
| شکست نوبت پس از ارسال پیام | حفظ اثر بیرونی و عدم ادعای rollback |
| ابزار افزوده در میانهٔ نوبت | پاسخ ابزار بدون deadlock و بدون انتظار برای پایان همان نوبت |
| دستور مخرب داخل پیام یا PR | APIهای بات binding و اعتبار نوبت را حفظ کنند؛ مهار همهٔ ابزارهای بومی ادعا نشود |
| ساخت/ویرایش فایل و git با ابزار بومی | رفتار مطابق اجرای مستقیم همان پروفایل، بدون محدودیت اضافهٔ بات |

دستورهای مقصد، پس از فاز یک:

```bash
uv sync --locked --group dev
uv run ruff check .
uv run ruff format --check .
uv run mypy src/peyda_pm_bot
uv run pytest
```

این دستورها تست آفلاین‌اند و به توکن یا CLI وصل نمی‌شوند. از فاز یک، چک زندهٔ همان فاز هم اجرا می‌شود و نتیجه‌اش جدا از pytest نوشته می‌شود. معیار، رفتار روی سرویس واقعی و بازیابی بعد از خرابی است.

تست زندهٔ تاپیک `pm` از همان فازی شروع می‌شود که آن رفتار ساخته شده: ذخیره و ACK، بعد یک نوبت و ابزار پیام/reply/ری‌اکشن، بعد حافظه، ایشو و گزارش. بحث دو نفر وقتی عضو دوم در دسترس است انجام می‌شود و تا آن زمان جای تست چندنفره اعلام نمی‌شود.

## ۹. تصمیم‌های باقیمانده و ترتیب حل

- **بستن فاز یک:** رفع نواقص ثبت‌شده در بخش ۱ و تکمیل مدرک ری‌استارت زنده. دریافت و ACK در ۲۰۲۶-۱۱-۲۱ روی تاپیک `pm` دیده شد؛ ACP هنوز اجرا نشده است.
- **فاز دو:** اجرای معمول پروفایل، load گفت‌وگوی موجود، transport ابزارهای افزوده، پیام/reply وسط کار، ری‌اکشن تنها، سکوت و `/screen` خصوصی.
- **فاز سه:** خواندن تصمیم قبلی با ایجنت واقعی.
- **فاز چهار:** مخزن مقصد، credential و یک ایشو آزمایشی. سیاست نقش‌ها و نام labelها هم اینجاست.
- **فاز پنج:** زمان گزارش، timezone و محل بکاپ. زمان داخلی UTC و نمایش اولیه Asia/Tehran است.
- **فاز شش:** سناریوی طولانی، sleep/wake و قطع اینترنت. اتصال اول این‌جا انجام نمی‌شود.

### موضوع‌هایی که پیش از پیاده‌سازی مربوط باید روشن شوند

اجرای عادی Antigravity، انتشار صریح با ابزار و اختیار ری‌اکشن تنها تصمیم قطعی‌اند. جدول زیر نقاط باز طراحی/آزمایش است، نه مجوز افزودن محدودیت تازه یا ادعای قابلیت ساخته‌شده.

| موضوع | تصمیم فعلی و چیزی که باید بررسی شود | موعد |
|---|---|---|
| پروفایل و اجازهٔ ابزار بومی | همان اجرای مستقیم؛ نسخه، مدل/حالت، DBus/keyring و نتیجهٔ permission واقعی مقایسه شوند. بات تنظیم جدیدِ محدودکننده یا auto-approve تحمیل نکند. | شروع فاز دو |
| transport ابزار افزوده | مسیر MCP/ACP احرازشده به همان نوبت؛ قابلیت HTTP/stdio و اتصال ابزار بدون جایگزینی ابزارهای بومی روی CLI واقعی آزمایش شود. نبود capability موفقیت ساختگی نیست. | شروع فاز دو |
| متن جلسه و خروجی گروه | فقط فراخوانی ابزار منتشر می‌شود. schema ارجاع پیام/نسخه، reply اختیاری و شناسهٔ درخواست تکرارپذیر نهایی شود. یک متن مشابه می‌تواند دو ارسال عمدی باشد. | فاز دو |
| ری‌اکشن مجاز و مقصد | تنظیم/تعویض/برداشتن ری‌اکشن خود بات در تاپیک؛ محدودیت emoji و پیام با Telegram و aiogram قفل‌شده تطبیق و زنده امتحان شود. شکست ابزار متن اجباری نسازد. دریافت ری‌اکشن اعضا جدا تصمیم‌گیری شود و رأی‌شماری ایجاد نکند. | فاز دو |
| انتشار فوری و شکست نوبت | پیام ارسال‌شده باقی می‌ماند. تلاش قبل از شبکه، مشاهدهٔ نتیجهٔ قبلی، pending پس از موفقیت، لغو ارسال‌نشده‌ها پس از شکست، ترتیب عملیات، chunkهای پیام بلند و unknown مستقل از retry نوبت طراحی شوند. | فاز دو |
| لغو و پیام حین کار | ingest ادامه دارد و ورودی عادی نگاه بعدی است. کنترل فنی توقف، actor مجاز و انقضای permission تعیین شوند؛ متن «صبر کن» بدون قابلیت steering تأییدشده تضمین توقف فوری نیست. | فاز دو |
| مالکیت نشست و اجرای دستی | قفل پروژه/پروفایل/گفت‌وگو و bot ID فراتر از مسیر DB؛ child یتیم، تست موازی و محدودیت تشخیص TUI دستی امتحان شوند. نشست دوم برای رفع خطا ساخته نشود. | فاز دو |
| ظرفیت backlog و رشد context | سقف واقعی prompt، رفتار compaction خود agy و زمان/بودجهٔ نوبت اندازه‌گیری شوند. منبع یا خط نخوانده حذف نشود؛ عبور از ظرفیت وضعیت قابل اقدام بسازد و بدون تصمیم ثبت‌شده backlog را به چند نوبت مستقل نشکند. | فاز دو |
| هویت و شواهد | نام نمایشی کنار user ID و ارجاع پیام باشد. edit، sender_chat/ناشناس، reply قدیمی و پیام حذف‌شده بدون فرض دریافت تاریخچه یا رویداد حذف بررسی شوند. | فازهای یک و دو |
| مرز اعتبارنامه و ابزار عادی | token بات تزریق نمی‌شود، ولی این کار sandbox فایل‌سیستم نیست. مسیر دادهٔ بات و cwd پروژه و احراز هویت ابزار افزوده مشخص شوند؛ `gh` معمول کاربر به‌عنوان مسیر کنترل‌شدهٔ adapter گزارش نشود. | فاز دو |
| خبر حافظه/ایشو بعد از commit | staged/queued موفقیت نیست؛ نتیجهٔ واقعی رویداد پایدار همان نشست است. wake-up، dedup و جلوگیری از حلقهٔ نتیجه و خبر زودهنگام آزمایش شوند. ابزار تلگرام برای واکنش به نتیجه استفاده شود. | فازهای سه و چهار |
| محدودیت نرخ و timeout | RetryAfter، deadline و ترتیب پایدار باشند؛ حد همزمانی جای نرخ نیست. سقف نوبت طولانی و رفتار subprocess بدون replay کورکورانهٔ کار واقعی تعیین شود. | از فاز دو |
| یادآوری و مزاحمت | ایجنت اجازهٔ سکوت دارد؛ scheduler نوبت بررسی‌شدهٔ بدون خروجی را شکست فرض نکند. timezone، ساعات سکوت و موعد یادآوری بدون تغییر با تیم نهایی شوند. | فاز پنج |
| متن، فایل و پیام غیرمتنی | نسخهٔ اول ورودی متنی است؛ caption، آلبوم، صوت و پیوست بدون بررسی قابلیت اضافه نشوند. حد پیام، متن فارسی و قالب‌بندی خروجی در payload و تست ابزار پیام پوشش داده شوند. | متن در فاز دو؛ رسانه فقط در صورت نیاز |

هیچ توکن یا credential در این سند، اسکیل‌ها، fixtures یا مخزن قرار نمی‌گیرد. پلن فعلی مجوز ارسال پیام به افراد نامشخص، تغییر سطح دسترسی یا انتشار/مرج کد ایجاد نمی‌کند.
