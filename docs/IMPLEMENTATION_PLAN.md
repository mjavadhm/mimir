# پلن پیاده‌سازی Peyda PM Bot

تاریخ: ۲۰۲۶-۱۱-۱۷ — وضعیت: فازهای یک تا چهار به‌صورت آفلاین پیاده شده‌اند؛ فازهای پنج و شش شروع نشده‌اند.

به‌روزرسانی ۲۰۲۶-۱۱-۱۸: به درخواست صریح کاربر، نصب CLI، اتصال سرویس‌ها و تست واقعی زودتر انجام می‌شود تا ناسازگاری‌ها پیش از ادامهٔ قابلیت‌ها پیدا شوند. این checkpoint، تکمیل کل فاز شش یا فاز پنج محسوب نمی‌شود؛ شواهد و محدودیت‌ها در [LIVE_TESTING.md](LIVE_TESTING.md) ثبت می‌شوند و جایگزین عبارت‌های قبلی دربارهٔ تعویق همهٔ تست‌های زنده‌اند.

این سند پلن اجرایی [README](../README.md) است. تصمیم‌های قطعی محصول در README مرجع‌اند؛ انتخاب‌های فنی زیر برای اجرای نسخه اول پیشنهاد می‌شوند و در شروع هر فاز با نتیجه آزمایش تطبیق داده می‌شوند.

اجرای فاز یک با درخواست صریح کاربر آغاز شد؛ وضعیت، راهنمای اجرا و محدودیت‌های آن در [PHASE_ONE.md](PHASE_ONE.md) ثبت شده است. قرارداد تفصیلی مرز ماژول‌ها، تراکنش‌ها و توسعه در [ARCHITECTURE.md](ARCHITECTURE.md) آمده است.

## ۱. نقطه شروع و محدوده

تحویل محصول دو مرحله مستقل دارد: **ابتدا بات مدیریت پروژه**، سپس **افزودن ریویو PR**. نصب و تست واقعی بات مدیریت در انتهای مرحله اول انجام می‌شود و منتظر توسعه ریویو نمی‌ماند.

- پیاده‌سازی از صفر با Python و aiogram 3؛ `tele-agy` فقط مرجع اتصال و رفتار ACP است.
- اجرای محلی روی لپ‌تاپ: یک پروژه، یک گروه مجاز، یک نشست Antigravity و حداکثر یک کار فعال ایجنت.
- طبق اعلام کاربر، بات به گروه اضافه شده و تاپیک `pm` ساخته شده است. شناسه عددی گروه، تاپیک و مدیر هنوز باید کشف و ثبت شوند؛ نام تاپیک کلید هویت نیست.
- تلگرام وب در Brave برای تست رابط در دسترس است؛ آزمون‌های خودکار به آن یا حساب شخصی وابسته نمی‌شوند.
- در بررسی قبلی، GUI نسخه 2.24.0 نصب بود، ولی `/usr/local/bin/agy` فقط لانچر GUI بود. نصب و کارکرد CLI واقعی هنوز تأیید نشده است.
- در بررسی محیط، Python 3.14.4 موجود بود و `uv` در PATH پیدا نشد. محیط مجازی و وابستگی‌های پروژه هنوز ساخته نشده‌اند.
- سرور عمومی، داشبورد، Mini App، مرج خودکار و دیپلوی خودکار در نسخه اول برنامه‌ریزی نمی‌شوند.

ترتیب اجرای مورد توافق: ابتدا توسعه قابلیت‌ها و آزمون‌های خودکار با اتصال‌های شبیه‌سازی‌شده؛ نصب CLI، ورود به سرویس‌ها و تست واقعی بات مدیریت در فاز آخر مرحله اول انجام می‌شوند. توسعه ریویو PR پس از تحویل این بات و در مرحله محصول مستقلی انجام می‌شود. نصب وابستگی‌های محیط توسعه و اجرای تست‌های آفلاین جزو کار هر فاز هستند.

اولین تحویل توسعه: مسیر دریافت، ذخیره و ارسال پیام با transport شبیه‌سازی‌شده و دیتابیس واقعی محلی کار کند. تحویل قابل استفاده با سرویس‌های واقعی، پس از یکپارچه‌سازی و پذیرش فاز شش است.

## ۳. معماری پیشنهادی

یک برنامه ماژولار در یک پردازش، با مرز روشن بین قواعد محصول و اتصال‌های بیرونی. هر فاز فقط ماژول‌های موردنیاز همان تحویل را اضافه می‌کند.

تقسیم قابلیت‌ها درون هر لایه انجام می‌شود: `conversations`، `memory`، `work` و `actions`؛ `reviews` فقط در مرحله دوم. هر قابلیت صاحب قواعد و داده خود است؛ ارتباط بین قابلیت‌ها از API عمومی application و DTOهای typed انجام می‌شود. ساختار زیر نمای لایه‌هاست، نه مجوز ایجاد فایل‌های بزرگ و همه‌منظوره برای هر لایه.

```text
Telegram getUpdates / GitHub polling
                  |
           durable inbox
                  |
        normalize + batch + queue
                  |
     one agent worker -> Antigravity ACP
                  |             |
          memory tools <--------+
                  |
      proposed action + policy check
                  |
       action executor -> GitHub
                  |
          durable outbox -> Telegram
```

دریافت ورودی، ارسال خروجی و تطبیق گیت‌هاب می‌توانند هنگام اجرای ایجنت فعال بمانند. صف ایجنت یک مصرف‌کننده دارد؛ این محدودیت در برنامه و تست اعمال می‌شود. در مرحله اول، خواندن وضعیت و پیوند PR برای هماهنگی تیم مجاز است؛ تحلیل diff، تولید یافته فنی و انتشار review به مرحله دوم تعلق دارند. ماژول، جدول و زمان‌بندی اختصاصی ریویو هنگام افزودن همان قابلیت ایجاد می‌شوند.

ساختار مقصد:

```text
src/peyda_pm_bot/
  __main__.py              # entry point
  bootstrap.py             # ساخت وابستگی‌ها و چرخه عمر برنامه
  config.py                # تنظیمات معتبر و بدون اسرار در خروجی
  domain/                  # مدل‌ها، قواعد نقش و انتقال وضعیت
  application/             # use caseها، هماهنگی صف، حافظه و اقدام‌ها
    ports.py               # Protocolهای کوچک فقط در مرزهای I/O
  adapters/
    telegram/              # polling، نرمال‌سازی، router و ارسال
    antigravity/           # ACP، رویدادها، permission و بازیابی نشست
    github/                # API، polling، تطبیق و snapshot
    storage/               # مدل‌های SQLAlchemy و repositoryها
    tools/                 # ابزارهای محدود حافظه و پیشنهاد اقدام
  runtime/                 # قفل پردازش، worker، زمان‌بندی و shutdown
migrations/
tests/{unit,integration,acceptance}/
docs/
```

جهت وابستگی: `application` به `domain` و قراردادهای I/O وابسته است؛ adapterها این قراردادها را پیاده می‌کنند. فقط `bootstrap` پیاده‌سازی‌های واقعی را به هم وصل می‌کند. مدل aiogram، ORM و JSON-RPC به قواعد دامنه نشت نمی‌کنند. بین ماژول‌ها handler دیگری را صدا نمی‌زنیم.

الگوهای مورد استفاده، با دلیل:

- **Ports & Adapters در مرز I/O:** تعویض ارتباط واقعی با fake بدون اجرای تلگرام یا مدل در تست.
- **Dependency Injection دستی:** انتقال وابستگی‌ها در سازنده یا پارامتر؛ بدون framework تزریق وابستگی.
- **Repository و تراکنش کوتاه:** جداکردن SQL و اتمیک‌کردن تغییرات مرتبط؛ بدون repository عمومی برای همه جدول‌ها.
- **Unit of Work سبک:** کنترل تراکنش از use case برای تغییر چند repository؛ commit در repository انجام نمی‌شود و عملیات شبکه خارج تراکنش باقی می‌ماند.
- **Inbox / Outbox:** ورودی پایدار پیش از تأیید دریافت؛ ارسال اعلان جدا از اجرای عملیات اصلی.
- **State Machine صریح:** انتقال‌های معتبر کار و اقدام (و ریویو در مرحله دوم)؛ تابع و enum کافی است، مگر پیچیدگی واقعی خلافش را ثابت کند.

برای هر کلاس، لایه یا الگوی جدید باید مسئله مشخصی وجود داشته باشد. microservice، Redis، Celery، event sourcing کامل و framework عمومی workflow برای نسخه اول لازم نیستند.

## ۴. ابزارهای توسعه و ذخیره‌سازی

| بخش | انتخاب پیشنهادی |
|---|---|
| Python | حداقل 3.12؛ نسخه محیط محلی پس از بررسی سازگاری وابستگی‌ها قفل می‌شود |
| وابستگی و محیط | `uv`، `pyproject.toml` و `uv.lock` |
| تلگرام | `aiogram 3`؛ نسخه دقیق هنگام ساخت lockfile |
| دیتابیس | SQLite محلی با WAL، foreign keys و busy timeout |
| دسترسی به داده | SQLAlchemy async با `aiosqlite`؛ `AsyncSession` جدا برای هر واحد کار |
| migration | Alembic؛ هر تغییر schema همراه migration قابل آزمایش |
| تنظیمات و ورودی ابزار | Pydantic و تنظیمات محیطی معتبر؛ اسرار خارج مخزن |
| کیفیت | Ruff برای lint/format و mypy strict برای کد برنامه |
| تست | pytest و pytest-asyncio؛ دیتابیس موقت و ساعت قابل تزریق |
| لاگ | logging ساخت‌یافته با شناسه کار/رویداد و حذف اسرار و متن خصوصی غیرضروری |

مبنای فعلی بررسی APIها aiogram 3.32.0 با پشتیبانی Bot API 10.4 است؛ نسخه‌ها نصب‌شده محسوب نمی‌شوند. هنگام ساخت lockfile آخرین انتشار پایدار و سازگاری بررسی می‌شود. برای قابلیت‌های جدید و نام/پارامتر دقیق، [مرجع Telegram و aiogram](TELEGRAM_BOT_API_REFERENCE.md) و قوانین AGENTS.md مبنا هستند.

وضعیت صف، زمان تجمیع پیام‌ها و offset ورودی در دیتابیس است؛ `asyncio.Queue` تنها می‌تواند نقش بیدارکردن worker را داشته باشد. هیچ تراکنشی هنگام انتظار برای مدل، شبکه یا تأیید انسانی باز نمی‌ماند. ORM session بین taskها مشترک نیست.

گروه داده‌ها به‌تدریج ایجاد می‌شوند: تنظیم پروژه و نقش‌ها؛ inbox و نسخه پیام‌ها؛ بسته‌ها و jobs؛ نشست و checkpoint؛ پرونده و پیوند شواهد و تصمیم‌ها؛ actions و approvals و attempts؛ outbox؛ وضعیت تطبیق ایشو/PR. داده‌های اختصاصی نسخه و مراحل ریویو در مرحله دوم اضافه می‌شوند. کلیدهای یکتای ورودی و روابط لازم از اولین migration مرتبط تعریف می‌شوند.

## ۵. قراردادهای پایداری و اختیار

1. یک قفل انحصاری سیستم‌عامل برای هر مسیر داده، اجرای همزمان نمونه دوم برنامه را رد می‌کند. worker تنها صاحب subprocess ایجنت است؛ قبل از جایگزینی، توقف پردازش قبلی تأیید می‌شود. بازیابی child باقی‌مانده پس از crash هم باید تست شود.
2. `getUpdates` در حلقه ورودی کوتاه اجرا می‌شود؛ updateها و offset بعدی در یک تراکنش ثبت می‌شوند، سپس درخواست تأییدکننده بعدی ارسال می‌شود. تکیه بر handlerهای پس‌زمینه پیش‌فرض برای تضمین ذخیره پیش از ACK کافی نیست. بعداً dispatcher از inbox تغذیه می‌شود. شکست ذخیره به معنی پیش‌نبردن offset است.
3. `update_id` تکراری اثر دوباره ندارد؛ ویرایش پیام نسخه جدید همان پیام است. دریافت ورودی و تکرار پردازش دو مفهوم جدا هستند.
4. زمان تجمیع اولیه: ۴ ثانیه سکوت با سقف ۱۲ ثانیه، قابل تنظیم. زمان‌بندی پس از ری‌استارت بازسازی می‌شود. تاپیک، reply و شناسه صریح تسک نشانه‌اند؛ نزدیکی زمانی اثبات یکی‌بودن موضوع نیست.
5. لغو و اصلاح صریح، نسخه درخواست و اقدام‌های وابسته را فوراً در لایه برنامه نامعتبر می‌کنند؛ تشخیص معنایی در نوبت ایجنت است. اقدام در انتظار تصمیم مبهم، پیش از رفع ابهام اجرا نمی‌شود.
6. تأیید به actor، نوع عملیات، مقصد و نسخه دقیق پیش‌نویس متصل است. executor پیش از ارسال، نقش و نسخه را دوباره می‌سنجد؛ تغییر یا لغو بعد از ارسال شبکه، تضمین بازگرداندن عملیات نیست.
7. حالت‌های اقدام: `draft → awaiting_approval → approved → executing → succeeded`، با مسیرهای `cancelled / stale / failed / unknown`. شکست ارسال اعلان، عملیات موفق را تکرار نمی‌کند.
8. عملیات گیت‌هاب با نتیجه نامعلوم پیش از retry تطبیق داده می‌شود. برای ساخت ایشو، شناسه پایدار اقدام در بدنه/metadata قابل جست‌وجو قرار می‌گیرد. برای تلگرام هم وضعیت نامعلوم ارسال جدا ثبت می‌شود؛ تضمین exactly-once نمی‌دهیم.
9. پیام‌های گروه، متن PR و کد منبع حق تغییر policy ندارند. ایجنت پیشنهاد می‌دهد؛ executor برنامه تصمیم دسترسی را اعمال می‌کند.
10. ابزارهای مدیریتی گیت‌هاب فقط از executor استفاده می‌کنند. اعتبارنامه گیت‌هاب و توکن تلگرام به محیط ایجنت داده نمی‌شوند. اجرای shell عمومی یا دسترسی به اعتبارنامه‌های میزبان نباید مسیر دورزدن executor ایجاد کند؛ قرارداد این محدودیت در توسعه تست می‌شود و اجرای واقعی آن در فاز شش تأیید می‌شود.
11. حافظه نسخه‌دار و مستند به پیام است. خلاصه با محدوده پوشش و منبع نگهداری می‌شود؛ تصمیم جایگزین‌شده حذف نمی‌شود. اصلاح پیوند پرونده یا تصمیم، پردازش‌های وابسته را برای بازبینی علامت می‌زند.
12. در مرحله دوم محصول، ریویو به `(repository, PR, base SHA, head SHA)` و checkpoint مرحله تعلق دارد. قبل از انتشار، نسخه دوباره تطبیق داده می‌شود.

## ۶. مرحله اول محصول — بات مدیریت پروژه

فازهای یک تا پنج با fake adapter و transport قابل کنترل آزمایش می‌شوند؛ پیاده‌سازی adapterهای واقعی براساس مستندات در همین فازها انجام می‌شود، اما نصب CLI و آزمون زنده به فاز شش موکول است. قابلیت‌های وابسته به نسخه نصب‌شده تا آن زمان «تأییدنشده» می‌مانند؛ موفقیت تست شبیه‌سازی‌شده به معنی کارکرد اتصال واقعی نیست.

### فاز یک — اسکلت و ذخیره مطمئن تلگرام

وضعیت: پیاده‌سازی آفلاین با ۳۵ تست موفق، Ruff و mypy strict؛ راهنمای اجرا و محدودیت‌ها در [تحویل فاز اول](PHASE_ONE.md). اتصال واقعی هنوز بررسی نشده است.

- محیط مجازی، ابزارهای کیفیت، تنظیمات، bootstrap و migration اولیه.
- تعیین owner و قرارداد هر قابلیت طبق ARCHITECTURE.md؛ بررسی خودکار مرز importها و lifecycle بدون اثر جانبی هنگام import. ابتدا آزمون rollback و ثبت اتمیک inbox/checkpoint با دیتابیس موقت، سپس مسیر دریافت پیام ساخته شود.
- allowlist گروه/تاپیک و مدیر، دریافت پایدار پیام و ویرایش، شناسه گوینده، reply، topic و ترتیب ورودی.
- قرارداد تنظیم شناسه‌ها و allowlist با داده آزمایشی؛ کشف شناسه واقعی `pm` و بررسی Privacy Mode در فاز شش. شناسه و نقش ناشناس به‌صورت خودکار مجاز نمی‌شوند.
- پاسخ محلی ساده برای سلامت سرویس و outbox اولیه؛ بدون ادعای اتصال مدل.

**تحویل:** اجرای محلی با transport آزمایشی و شبیه‌سازی قطع شبکه؛ crash بین دریافت و ACK باعث گم‌شدن پیام نشود و update تکراری رکورد/کار مضاعف نسازد. پیام خارج محدوده وارد پردازش محصول نشود.

### فاز دو — صف و قرارداد مکالمه تک‌نشستی

وضعیت: پیاده‌سازی آفلاین؛ قراردادها، اجرا و محدودیت‌های آن در [PHASE_TWO.md](PHASE_TWO.md).

- بسته‌بندی پایدار پیام‌ها، صف و بازیابی کار ناتمام، timeout و retry محدود با backoff.
- یک agent worker با قفل پردازش، مدیریت subprocess و shutdown؛ ذخیره session ID و checkpoint.
- تعریف قرارداد اتصال Antigravity و پیاده‌سازی ACP براساس مستندات؛ fake agent و subprocess آزمایشی برای تست streaming، permission، cancellation، resume و خطاها بدون نصب CLI. روش اتصال ابزارهای حافظه براساس پروتکل/SDK مستند طراحی و تأیید عملی آن به فاز شش موکول می‌شود.
- ثبت ورودی جدید هنگام پاسخ طولانی؛ پاسخ نهایی در همان گروه و تاپیک با حفظ reply در صورت امکان.
- انتخاب کارها با زمان انتظار برای گفتگو، ثبت تصمیم و درخواست‌های مدیریت؛ سیاست اولیه قابل تنظیم و تست جلوگیری از گرسنگی صف. زمان‌بندی ریویو در مرحله دوم اضافه می‌شود.

**تحویل:** با ورودی آزمایشی دو گوینده و پیام‌های تکه‌تکه، فقط یک کار fake agent فعال بماند؛ بازیابی نشست و توقف پردازش قبلی با subprocess آزمایشی بررسی شود. توانایی واقعی Antigravity هنوز تأییدنشده است.

### فاز سه — پرونده و حافظه مستند

وضعیت: پیاده‌سازی آفلاین با ۹۴ تست موفق؛ قرارداد ابزارها، اجرا و محدودیت‌ها در [PHASE_THREE.md](PHASE_THREE.md). سیاست توافق و موارد حساس مطابق خواسته کاربر فقط در متن ایجنت است.

- ابزارهای محدود جست‌وجو، خواندن و به‌روزرسانی پرونده با کنترل شناسه پروژه و schema ورودی.
- ارتباط چندبه‌چند پیام/پرونده؛ تفکیک پیشنهاد، تصمیم، تعهد و برداشت؛ نسخه‌بندی و منبع.
- جست‌وجوی متنی و alias برای شروع؛ ارزیابی FTS با متن فارسی پیش از استفاده. دیتابیس برداری فقط در صورت ضعف قابل اندازه‌گیری جست‌وجو بررسی می‌شود.
- خلاصه‌های تدریجی با بودجه زمینه و شواهد اصلی؛ ابزار اصلاح پیوند نادرست و تصمیم قبلی.
- تهیه متن پیشنهادی تصمیم معماری در حافظه؛ نوشتن در فایل‌های مخزن پروژه به درخواست کاربر در این فاز انجام نمی‌شود.

**تحویل:** در سناریوی آفلاین تغییر موضوع، ری‌استارت و بازگشت به بحث، ابزار حافظه تصمیم قبلی را با منبع برگرداند؛ پیوند چند پرونده و اصلاح سابقه تست شوند. ارزیابی تشخیص معنایی با ایجنت واقعی در فاز شش انجام می‌شود.

### فاز چهار — ساخت ایشو و هماهنگی شروع کار

وضعیت: پیاده‌سازی آفلاین با ۱۳۳ تست موفق و Ruff/mypy؛ قرارداد و اجرای نمونه در [PHASE_FOUR.md](PHASE_FOUR.md). طبق انتخاب تازه کاربر، توافق و تأیید تیم فقط در پرامپت است؛ submit نسخه مشخص و کنترل فنی اجرا در کد هستند.

- پیاده‌سازی اتصال گیت‌هاب، جست‌وجوی ایشو و PR مشابه و خواندن کد مرتبط با fake transport؛ اتصال حساب واقعی در فاز شش.
- پیش‌نویس شامل محدوده، معیار پایان، مسئول پیشنهادی و وابستگی؛ پیش‌نویس و submit نسخه‌دار؛ توافق انسانی طبق پرامپت تیم، بدون approval engine.
- executor مستقل برای ساخت/تکمیل ایشو، ثبت تلاش و تطبیق نتیجه نامعلوم؛ اطلاع‌رسانی از outbox.
- اعلام شروع، بررسی هم‌پوشانی، پیش‌نیاز و کار نیمه‌تمام؛ نگاشت اولیه وضعیت‌ها به labels با نام‌های قابل تنظیم، بدون اجبار GitHub Projects.

**تحویل:** لغو پیش از اجرا، grant نامعتبر و submit پیش‌نویس قدیمی رد شوند؛ شبیه‌سازی موفقیت ساخت ایشو و گم‌شدن پاسخ باعث retry تکراری نشود؛ شکست ارسال تلگرام عملیات اصلی را تکرار نکند.

### فاز پنج — پیگیری و آماده‌سازی استفاده روزمره

- گزارش درخواستی، مانع و اقدام بعدی؛ یادآوری با زمان‌بندی قابل تنظیم، dedup و جلوگیری از اعلان بدون تغییر.
- تطبیق دوره‌ای گیت‌هاب، بررسی محافظت main و مستندسازی تنظیمات لازم؛ تغییر قواعد مخزن عملیات جدا و با اختیار مشخص است.
- بکاپ سازگار SQLite و آزمون restore، سیاست نگهداری/حذف پیام و پیوست، راهنمای نصب و رفع قطعی ورود.
- آماده‌کردن اجرای سرویس محلی با restart کنترل‌شده، ابزار اندازه‌گیری منابع و سناریوهای sleep/wake و قطع اینترنت برای پذیرش نهایی.

**تحویل:** گزارش، زمان‌بندی، بکاپ و restore در تست محلی آفلاین تأیید شوند؛ کد و راهنمای اجرا برای یکپارچه‌سازی واقعی آماده باشند. مرج همچنان انسانی است.

### فاز شش — نصب، یکپارچه‌سازی و تست واقعی نهایی

- نصب CLI رسمی در کنار GUI، بدون جایگزینی لانچر فعلی؛ ثبت مسیر کامل binary در تنظیمات بات و انجام ورود لازم.
- تست نسخه، ACP initialize، ساخت نشست، دو prompt پیاپی، streaming، resume/load، tool call، permission، cancellation و خطاهای ورود/قطع ارتباط.
- اتصال و آزمون ابزارهای حافظه و آزمون مجوزهای عملیات اثرگذار. خواندن فایل با رفتار فعلی Antigravity پذیرفته شده و محدودسازی اضافهٔ خواندن از معیار تحویل خارج است.
- افزودن و آزمون ساخت فایل تازهٔ موردنیاز کار داخل روت پروژه. آزمون باید ساخت فایل جدید را تأیید کند و بازنویسی فایل موجود یا ساخت فایل بیرون روت را رد کند، از جمله مسیرهایی که با پیوند نمادین از روت خارج می‌شوند.
- افزودن مسیر اجرای روزمره که دریافت تلگرام، نشست موجود Antigravity، همگام‌سازی GitHub، یادآوری و outbox را با هم راه بیندازد. حالت‌های فعلی تست اتصال مسیرهای کوتاه و مستقل هستند.
- کشف و ثبت شناسه واقعی گروه، تاپیک `pm` و مدیر؛ بررسی دریافت پیام معمول گروه و Privacy Mode با کاربر.
- اتصال مخزن و حساب آزمایشی گیت‌هاب با سطح دسترسی مشخص و اجرای سناریوهای ساخت ایشو، تأیید، لغو و تطبیق وضعیت تسک/PR در محدوده مجاز؛ انتشار review در این تحویل انجام نمی‌شود.
- اجرای تست سرتاسری در تلگرام وب/اپ: پیام‌های تکه‌تکه و چندنفره، تغییر موضوع، بازیابی تصمیم، اصلاح درخواست، تغییر وضعیت تسک و ری‌استارت حین کار.
- تست sleep/wake لپ‌تاپ، قطع اینترنت و بازیابی؛ اندازه‌گیری RAM/CPU برنامه و Antigravity جداگانه و یک روز استفاده آزمایشی.

**تحویل:** گزارش اتصال‌های واقعی با transcript پاک‌سازی‌شده، رفع ناسازگاری‌ها، نتیجه سناریوهای پذیرش مدیریتی README و تأیید بازیابی صف و داده بدون اثر تکراری. اتصال‌های تأییدنشده یا تست‌های انجام‌نشده صریح ثبت می‌شوند. فعال‌سازی هر عملیات اثرگذار به تأیید مجوز همان مسیر وابسته است.

## ۷. مرحله دوم محصول — افزودن ریویو PR

این مرحله پس از تحویل و تست واقعی بات مدیریت شروع می‌شود و شرط آماده‌شدن مرحله اول نیست. پلن مستقل در [PR_REVIEW_PLAN.md](PR_REVIEW_PLAN.md) آمده است. قابلیت ریویو به همان بات، همان ایجنت و همان نشست افزوده می‌شود؛ بات یا نشست دوم ساخته نمی‌شود.

## ۸. آزمون‌ها و معیار کیفیت

Unit test برای انتقال وضعیت، policy، تازگی تأیید، تجمیع و انتخاب صف. Integration test با SQLite فایل‌محور موقت برای migration، قفل، inbox/outbox و recovery؛ دیتابیس حافظه‌ای به‌تنهایی رفتار فایل و WAL را ثابت نمی‌کند. Adapterها با fake transport و رویداد واقعی پاک‌سازی‌شده آزمایش می‌شوند.

سناریوهای اجباری مرحله اول محصول؛ سناریوهای ریویو در پلن مستقل مرحله دوم آمده‌اند:

| سناریو | انتظار |
|---|---|
| crash پس از ذخیره inbox و پیش از ACK | بازپخش بدون اثر مضاعف |
| crash حین عملیات بیرونی | ثبت unknown و تطبیق پیش از retry |
| اجرای نمونه دوم برنامه یا child قدیمی | جلوگیری از دو ایجنت فعال |
| ویرایش/لغو حین انتظار | نامعتبرشدن نسخه قبلی و اقدام وابسته |
| رد یا انقضای تأیید | عدم اجرا و اعلام وضعیت واقعی |
| قطع نشست و ورود منقضی | حفظ صف و خطای قابل اقدام |
| بار پیوسته گفتگو و درخواست مدیریت | پیشرفت کارها بدون starvation |
| outbox ناموفق | retry ارسال بدون تکرار ساخت ایشو |
| دستور مخرب داخل پیام یا PR | عدم تغییر policy و عدم دورزدن executor |

دستورهای مقصد، پس از فاز یک:

```bash
uv sync --locked --group dev
uv run ruff check .
uv run ruff format --check .
uv run mypy src/peyda_pm_bot
uv run pytest
```

این دستورها پس از ساخت محیط توسعه قابل اجرا هستند؛ راهنمای فاز یک نتیجه بررسی‌های آفلاین را توضیح می‌دهد. تست‌های خودکار آفلاین در هر فاز توسعه اجرا می‌شوند؛ نصب CLI و تست واقعی تلگرام/ACP/GitHub فقط در فاز شش و با محیط آزمایشی انجام می‌شوند. معیار، رفتار صحیح و بازیابی است، نه درصد پوشش دلخواه یا تست‌هایی که فقط شکل پیاده‌سازی را تکرار می‌کنند.

تست دستی در تاپیک `pm`: پیام‌های تکه‌تکه، بحث دو نفر، تغییر موضوع و بازگشت، اصلاح/لغو، درخواست وضعیت و ری‌استارت حین پاسخ. تست مجوز نفر دوم به یک عضو واقعی دوم نیاز دارد؛ تا آن زمان آزمون خودکار مکمل است و جای تست دستی چندنفره گزارش نمی‌شود.

## ۹. تصمیم‌های باقیمانده و ترتیب حل

- **هنگام توسعه قراردادها:** روش حافظه و مدیریت نشست — فاز دو؛ سیاست نقش‌ها و نگاشت labels — فاز چهار؛ تأیید با نمونه واقعی در فاز شش.
- **پیش از اتصال واقعی:** محل/نسخه CLI، ورود، تأیید محدودسازی ابزار و قرارداد حافظه — فاز شش.
- **پیش از دریافت گروه واقعی:** شناسه گروه و تاپیک، مدیر بات و دریافت پیام‌های عادی — فاز شش.
- **پیش از نوشتن گیت‌هاب واقعی:** مخزن مقصد، روش credential و تطبیق نقش اعضا — فاز شش.
- **آماده‌سازی استفاده روزمره:** زمان گزارش، timezone نمایشی، سیاست نگهداری داده و محل بکاپ — فاز پنج؛ تنظیم مقادیر واقعی و پذیرش در فاز شش. زمان داخلی UTC و نمایش اولیه Asia/Tehran است.

هیچ توکن یا credential در این سند، اسکیل‌ها، fixtures یا مخزن قرار نمی‌گیرد. پلن فعلی مجوز ارسال پیام به افراد نامشخص، تغییر سطح دسترسی یا انتشار/مرج کد ایجاد نمی‌کند.
