# تحویل فاز اول

تاریخ: ۲۰۲۶-۱۱-۱۷. این تحویل مسیر آفلاین دریافت، ذخیره، پردازش و ارسال آزمایشی را پیاده می‌کند. قابلیت‌های مدیریتی و اتصال Antigravity در فازهای بعد قرار دارند.

## اجرا و بررسی

Python محیط بررسی: **3.14.4**. نسخه دقیق تمام وابستگی‌ها در `uv.lock` ثبت شده؛ aiogram **3.32.0** است. بازه پشتیبانی اعلام‌شده Python از 3.12 تا قبل از 3.15 است؛ در این تحویل فقط 3.14.4 اجرا شده است.

از ریشه checkout:

```bash
uv sync --locked --group dev
uv run ruff check .
uv run ruff format --check .
uv run mypy src/peyda_pm_bot
uv run pytest
uv run python -m peyda_pm_bot --database /tmp/peyda-demo.db
```

در محیط ساخته‌شده این تحویل، uv در `.venv/bin/uv` نیز در دسترس است؛ با `source .venv/bin/activate` فرمان‌های بالا قابل استفاده‌اند. اگر uv در PATH نیست، ابزارهای نصب‌شده محیط با `.venv/bin/ruff`، `.venv/bin/mypy`، `.venv/bin/pytest` و `.venv/bin/python` نیز قابل اجرا هستند. uv ابزار راه‌اندازی اولیه است؛ نصب وابستگی‌ها به دسترسی شبکه نیاز دارد، اما تست‌ها و دمو شبکه مصرف نمی‌کنند. CI همان بررسی‌ها را اجرا می‌کند؛ انتشار CI هنوز مستلزم ایجاد مخزن و push است.

دمو هر بار یک پیام `/health` جدید از مدیر آزمایشی می‌سازد، آن را در دیتابیس نگه می‌دارد و پاسخ را به fake transport تحویل می‌دهد. فایل دیتابیس و پوشه والد باید قابل نوشتن باشند. توکن، `.env` یا ورود واقعی لازم نیست. نمونه شناسه‌ها واقعی نیستند. این نسخه از checkout اجرا می‌شود؛ بسته‌بندی مستقل migrationها برای توزیع wheel جزو این تحویل نیست.

## رفتار و قراردادها

- `bootstrap.application(settings, transport)` مالک قفل پردازش، اجرای migration، بازیابی و بستن منابع است. `runtime.runner.run` دریافت، پردازش و ارسال را به‌صورت taskهای تحت نظارت اجرا می‌کند؛ caller رویداد توقف را تنظیم می‌کند.
- تنظیمات معتبر در `config.Settings` هستند؛ نمونه متغیرها در `.env.example` آمده است. شناسه مدیر باید مثبت باشد و گروه، تاپیک و مجموعه مدیران باید صریح باشند. دمو از مقادیر آزمایشی مشخص استفاده می‌کند.
- `IncomingUpdate` و `MessageEvent` قرارداد مستقل از aiogram هستند. نسخه‌های پیام با هویت گوینده، نام ثبت‌شده، sender chat، reply، زمان UTC و منشأ update حفظ می‌شوند. نام گوینده جای شناسه یا مجوز را نمی‌گیرد.
- پیام مجاز عضو عادی ذخیره می‌شود؛ پاسخ سلامت فقط برای متن دقیق `/health` از مدیر مجاز، در گروه و تاپیک مجاز و برای پیام اصلی ساخته می‌شود. پیام ویرایش‌شده و هویت ناشناس/ارسال از طرف chat اجازه پاسخ مدیریتی ندارند. فرمان دارای پسوند `@username` فعلاً پشتیبانی نمی‌شود.
- برای ورودی خارج محدوده و update پشتیبانی‌نشده، فقط شناسه، نوع و وضعیت ignored نگهداری می‌شود؛ متن خصوصی آن وارد inbox نمی‌شود. checkpoint از آن عبور می‌کند.
- inbox و offset در یک تراکنش ثبت می‌شوند. درخواست `getUpdates` بعدی فقط offset ذخیره‌شده را می‌فرستد. پایان پردازش، نسخه پیام و پاسخ outbox نیز یک تراکنش دارند. پردازش به ترتیب update ID است.
- SQLite فایل‌محور، WAL، foreign keys و busy timeout پنج‌ثانیه‌ای دارد؛ `BEGIN IMMEDIATE` تراکنش‌های کوتاه و claimها را بین اتصال‌ها سری می‌کند. شبکه بیرون تراکنش است. دیتابیس به یک project ID متصل می‌شود.
- `TemporaryFailure` یعنی درخواست ارسال قطعاً پذیرفته نشده و retry مجاز است. شبکه/timeout نامطمئن هنگام ارسال، `unknown` می‌شود. حداکثر سه تلاش ارسال، backoff نمایی با پایه یک ثانیه و رعایت retry-after پیش‌فرض است؛ Sender این مقادیر را از تنظیمات می‌گیرد. timeout ارسال ۳۰ ثانیه است.
- دریافت پس از شش خطای موقت متوالی برنامه را با خطا متوقف می‌کند؛ قبل از آن backoff و retry-after رعایت می‌شوند. موفقیت دریافت شمارنده را صفر می‌کند. restart باید پس از رفع مشکل انجام شود.
- claim ارسال پیش از شبکه commit می‌شود. startup وضعیت `sending` باقی‌مانده را `unknown` می‌کند. این تصمیم ممکن است ارسال انجام‌نشده را نیز متوقف کند؛ اولویت جلوگیری از تکرار کورکورانه است. unknown/failed خودکار دوباره صف نمی‌شوند؛ ابزار تطبیق دستی در این فاز ارائه نشده است.
- قفل فایل Linux از دو نمونه برنامه روی یک مسیر دیتابیس جلوگیری می‌کند؛ بازیابی فقط زیر همین قفل انجام شود. checkpoint فعلاً مخصوص یک پروژه/یک بات است؛ اتصال بات دیگری به همان دیتابیس مجاز نیست.
- adapter واقعی aiogram پیاده و با session شبیه‌سازی‌شده آزموده شده است. executable عمداً مسیر live ندارد؛ Privacy Mode، شناسه‌ها و سازگاری واقعی در فاز شش بررسی می‌شوند.

## شواهد و محدودیت‌ها

نتیجه اجرای این تحویل: **۳۵ تست موفق**، Ruff check و format check موفق، و mypy strict بدون خطا روی ۲۳ فایل منبع. دمو با SQLite واقعی اجرا شد و یک پاسخ سلامت به fake transport تحویل داد. اجرای pytest در sandbox محدود متوقف ماند؛ اجرای کامل و موفق خارج از همان sandbox و همچنان بدون اتصال به سرویس‌ها انجام شد. CI تعریف شده، اما روی GitHub اجرا نشده است.

آزمون‌های پذیرش از SQLite فایل‌محور موقت و transport آزمایشی استفاده می‌کنند: rollback، شکست batch، replay پیش از ACK، ویرایش، allowlist، هویت ناشناس، atomic outbox، restart، claim همزمان، retry-after، نتیجه نامعلوم، شکست ثبت نتیجه پس از ارسال، shutdown و cleanup راه‌اندازی ناموفق. کنترل import، چرخه وابستگی و اثر جانبی import نیز خودکار است.

تست زنده تلگرام، Antigravity و GitHub اجرا نشده است. ضمانت exactly-once برای ارسال خارجی وجود ندارد. بازیابی فقط ورودی‌هایی را پوشش می‌دهد که سرویس واقعاً دریافت کرده؛ تاریخچه از دسترس خارج‌شده تلگرام بازیابی خودکار ندارد. تأیید اجرایی shutdown و شبکه صرفاً آفلاین است.

منابع قرارداد adapter در تاریخ همین تحویل: [Telegram getUpdates](https://core.telegram.org/bots/api#getupdates)، [aiogram getUpdates](https://docs.aiogram.dev/en/latest/api/methods/get_updates.html) و کد نصب‌شده aiogram 3.32.0. `edit_date` در این نسخه `int | None` است و در adapter به datetime UTC تبدیل می‌شود؛ `date` از ابتدا datetime است.
