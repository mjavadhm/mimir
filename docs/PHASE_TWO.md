# تحویل فاز دوم — صف و مکالمه تک‌نشستی

تاریخ: ۲۰۲۶-۱۱-۱۷. این فاز با SQLite فایل‌محور، transport و agent آزمایشی قابل اجراست. CLI واقعی Antigravity نصب نشده و اتصال زنده تلگرام، ACP و GitHub آزمایش نشده است.

## اجرای نمونه

از ریشه checkout با محیط توسعه موجود:

```bash
source .venv/bin/activate
uv sync --locked --group dev
uv run python -m peyda_pm_bot --phase-two --database /tmp/peyda-phase-two.db
uv run ruff check .
uv run ruff format --check .
uv run mypy src/peyda_pm_bot
uv run pytest
```

دمو دو پیام از دو گوینده می‌سازد، پس از تجمیع یک job به همان نشست fake می‌فرستد و کارت وضعیت و پاسخ نهایی را به fake transport تحویل می‌دهد. برای دمو فاز یک، از دیتابیس دیگری و بدون `--phase-two` استفاده کنید. اجرای پیوسته از `runtime.runner.run(..., agent_worker=app.worker)` در context متعلق به `bootstrap.application` انجام می‌شود؛ caller مالک رویداد توقف است. executable فعلی فقط دمو آفلاین دارد.

## رفتار پیاده‌شده

- مسیر دریافت و ACK فاز اول حفظ شده است. ثبت نسخه پیام، افزودن آن به job و پایان پردازش inbox یک تراکنش است؛ پیام‌های قبلاً پردازش‌شده به‌طور خودکار بازپخش نمی‌شوند.
- bootstrap تجمیع را فعال می‌کند. پیام‌های عادی با چهار ثانیه سکوت و سقف دوازده ثانیه بسته می‌شوند. هر بسته حداکثر ۵۰ پیام یا ۳۲ هزار نویسه دارد؛ یک پیام منفرد بدون قطع‌کردن شواهد حفظ می‌شود. deadlineها پایدارند. ترتیب انتخاب، due سپس شناسه job است.
- بسته واحد انتقال است، نه اثبات هم‌موضوع بودن پیام‌ها. گوینده، reply و نسخه هر پیام در snapshot حفظ می‌شوند. ویرایش pending نسخه آن را تغییر می‌دهد؛ ویرایش running آن را superseded و اصلاح را وارد نوبت بعدی می‌کند. پاسخ‌های pending مبتنی بر پیام اصلاح‌شده نامعتبر می‌شوند؛ ارسال انجام‌شده قابل بازگرداندن نیست.
- worker یک قفل محلی و دیتابیس یک قید یکتای job فعال دارد. root یک worker و یک نشست برای پروژه می‌سازد؛ از ساخت worker/adapter مستقل موازی برای همان پروژه خودداری شود. ورودی جدید تا نوبت بعد صف می‌ماند.
- session ID، نسل اتصال، وضعیت job، تعداد تلاش، نسخه و نتیجه ذخیره می‌شوند. نتیجه نهایی تنها با نسخه معتبر و مقصد داخل snapshot پذیرفته می‌شود. `reply` می‌تواند فهرستی از پیام‌ها و ری‌اکشن‌ها بسازد و `silent` بدون عملیات است؛ متن تدریجی و فکر داخلی منتشر نمی‌شود.
- پایان موفق و outbox اتمیک‌اند. پاسخ طولانی به قطعه‌های ۳۵۰۰ نویسه تقسیم می‌شود؛ هر قطعه کلید یکتا و وابستگی به موفقیت قبلی دارد. شکست ارسال یا unknown اجرای دوباره ایجنت را راه نمی‌اندازد.
- کارت وضعیت یک شناسه پایدار دارد، تعداد pendingها را نمایش می‌دهد و با فاصله حداقل سه ثانیه ویرایش می‌شود. تغییر pending ادغام می‌شود. ساخت کارت با نتیجه unknown تکرار نمی‌شود؛ شکست ویرایش کارت امکان یک ساخت مجدد می‌دهد؛ شکست ساخت کارت نیازمند رسیدگی است و حلقه ساخت مکرر ایجاد نمی‌کند. ویرایش‌ها با شناسه همان پیام به transport می‌روند.

## کنترل و حدود دسترسی

فقط مدیر allowlist با هویت مشخص، در تاپیک مجاز و با پیام اصلی می‌تواند این فرمان‌ها را اجرا کند:

- `/health` سلامت ذخیره‌سازی.
- `/status` کار فعال، تعداد منتظرها و blocked بودن صف.
- `/cancel JOB_ID` لغو pending/running/unknown و جلوگیری از انتشار پاسخ دیررس.
- `/retry JOB_ID` تلاش صریح تازه برای failed/unknown با حفظ سابقه؛ ناشناخته بودن نتیجه قبلی باید توسط مدیر بررسی شده باشد.
- `/turbo status`، `/turbo on` و `/turbo off` مشاهده یا ثبت حالت درخواستی؛ حالت مؤثر جدا نمایش داده می‌شود.

Turbo در fake آزموده می‌شود. adapter واقعی فعلاً `set_turbo` را تأیید نمی‌کند، چون روش تغییر session-scoped آن برای CLI نصب‌شده احراز نشده است. عدم تأیید هیچ‌گاه موفقیت گزارش نمی‌شود؛ حالت درخواستی موجب عبور خودکار از permissionها نیست. نام flag یا API فرضی اضافه نشده است.

policy خواندن مسیرهای مشخص پروژه را مجاز می‌کند و نوشتن، shell، مسیر بیرون پروژه، symlink خروجی و مسیرهای شناخته‌شده اسرار را رد می‌کند. توکن تلگرام و credential گیت‌هاب در محیط child قرار نمی‌گیرند. این policy جای محدودسازی سیستم‌عامل یا قواعد داخلی ابزارهای خود Antigravity نیست. به همین دلیل `AcpAgent` تا وقتی `validated_environment` به‌طور صریح پس از بررسی فاز شش تأیید نشود، از راه‌اندازی خودداری می‌کند. CLI فعلی هیچ مسیر فعال‌سازی live ندارد.

## پایداری و subprocess

- startup job باقی‌مانده در running را unknown می‌کند و صف ایجنت را متوقف نگه می‌دارد؛ ذخیره ورودی و اطلاع‌رسانی می‌توانند ادامه پیدا کنند. مدیر با retry یا cancel صریح آن را تعیین تکلیف می‌کند.
- راه‌اندازی حداکثر سه تلاش برای خطای قطعاً موقت دارد؛ تلاش‌های بعدی یک و دو ثانیه تأخیر دارند. پاسخ مبهم پس از ارسال prompt خودکار تکرار نمی‌شود. نداشتن پشتیبانی load نشست موجب ساخت بی‌صدای نشست تازه نمی‌شود.
- مقادیر تنظیم‌پذیر در `.env.example`: زمان سکوت، سقف تجمیع، timeout راه‌اندازی ۳۰ ثانیه، نوبت ۶۰۰ ثانیه و مهلت لغو ۵ ثانیه. تنظیمات از bootstrap به worker منتقل می‌شوند.
- supervisor لینوکسی با guardian مستقل و parent-death signal، گروه پردازش child را پس از مرگ والد متوقف می‌کند. قفل فایل به guardian ارث می‌رسد. قبل از اجرای جایگزین، پردازش قبلی باید پایان یافته باشد.
- در composition مربوط به ACP، PID و زمان شروع guardian در فایل محلی کنار دیتابیس ثبت می‌شوند. PID تنها مبنای کشتن یک پردازش نیست؛ سابقه نامطمئن یا پردازش قبلی زنده، اجرای جایگزین را رد می‌کند. فایل خراب نیازمند رسیدگی است و خودکار نادیده گرفته نمی‌شود.
- shutdown نوبت را لغو، اتصال را بسته و process را متوقف می‌کند. آزمون‌ها هم توقف عادی و هم مرگ والد را با process آزمایشی پوشش می‌دهند. ابزار بیرونی‌ای که عمداً از گروه پردازش جدا شود به کنترل محیط فاز شش نیاز دارد.

## قرارداد ACP و شواهد

SDK رسمی `agent-client-protocol==1.0.0` قفل شده است. adapter از initialize، new/load session، prompt، session updates و cancel استفاده می‌کند. قابلیت load از handshake بررسی می‌شود؛ پاسخ JSON نهایی با Pydantic اعتبارسنجی می‌شود. ابزارهای حافظه فاز سه از فهرست MCP در ساخت/بازکردن نشست متصل خواهند شد؛ در این فاز فهرست خالی است.

مرجع‌ها: [SDK رسمی Python](https://agentclientprotocol.com/libraries/python)، [نشست ACP](https://agentclientprotocol.com/protocol/v1/session-setup)، [Antigravity ACP](https://antigravity.google/docs/ide/extensions/acp/)، [مجوزها و Turbo](https://antigravity.google/docs/permissions)، [ویرایش پیام aiogram](https://docs.aiogram.dev/en/latest/api/methods/edit_message_text.html). قرارداد به SDK نصب‌شده متکی است؛ پشتیبانی CLI واقعی هنوز اثبات نشده است.

آزمون‌های فاز دوم شامل بسته‌بندی، سقف انتظار، نسخه ویرایش، claim انحصاری، سکوت و پاسخ، ترتیب قطعه‌های خروجی، resume همان نشست، permission، Turbo در fake، لغو، timeout، unknown، کارت، قفل worker و process guardian هستند. تست پروتکل یک peer JSON-RPC مستقل را به SDK متصل می‌کند؛ این تست سازگاری زنده Antigravity نیست. بررسی‌های فاز اول نیز حفظ شده‌اند. CI تعریف شده اما روی GitHub اجرا نشده است.

Migration جدید داده‌های outbox فاز یک را منتقل می‌کند. downgrade بعد از ایجاد تاریخچه job عمداً رد می‌شود؛ برای بازگشت، بکاپ پیش از ارتقا لازم است. مهاجرت و تطابق مدل SQL با schema در تست‌ها بررسی می‌شوند.

## نتیجه بررسی این تحویل

**۵۵ تست آفلاین موفق در تحویل اولیه**؛ Ruff check و format check موفق؛ mypy strict بدون خطا روی ۳۵ فایل منبع؛ `uv sync --locked --offline --group dev` موفق. دمو دوگوینده با دیتابیس واقعی اجرا شد و یک job با حداکثر یک نوبت ایجنت فعال، کارت وضعیت و پاسخ نهایی تحویل داد. تست‌ها به دلیل محدودیت اجرای async SQLite در sandbox، خارج از همان sandbox اجرا شدند؛ transport سرویس‌ها همچنان آزمایشی بود.

کنترل‌های ذخیره‌سازی ورودی و خروجی از طریق Protocolهای جدا در همان Unit of Work مصرف می‌شوند. نمای `store` صرفاً برای سازگاری فاز اول باقی مانده و پیاده‌سازی موازی ذخیره‌سازی ساخته نشده است.


## تکمیل فاز دو — چند پیام و ری‌اکشن (۲۰۲۶-۱۱-۱۸)

در یک نوبت، ایجنت می‌تواند چند پیام با ریپلای‌های متفاوت، پیام بدون ریپلای، یک جمع‌بندی یا فقط ری‌اکشن تولید کند. تصمیم زمان استفاده و سبک پاسخ در این تغییر تنظیم نشده است؛ فقط قرارداد قابلیت‌ها به پرامپت اتصال معرفی شده است. این ابزارهای خروجی به‌صورت actionهای typed در نتیجه نهایی نوبت ارائه می‌شوند؛ اجرای مستقیم MCP ابزار تلگرام در میانه نوبت اضافه نشده است.

قرارداد خروجی جدید:

```json
{
  "disposition": "reply",
  "actions": [
    {"kind": "message", "text": "پاسخ نفر اول", "reply_to_id": 100},
    {"kind": "message", "text": "پاسخ نفر دوم", "reply_to_id": 101},
    {"kind": "message", "text": "جمع‌بندی مشترک", "reply_to_id": null},
    {"kind": "reaction", "message_id": 101, "emoji": "👍"}
  ]
}
```

- `reply_to_id: null` یا نبود آن در action پیام یعنی ارسال بدون ریپلای. برای برداشتن ری‌اکشن خود بات، `emoji: null` فرستاده می‌شود. `silent` باید هیچ خروجی‌ای نداشته باشد.
- هدف ریپلای یا ری‌اکشن باید از پیام‌های همان snapshot باشد؛ ایجنت نمی‌تواند گروه/تاپیک دیگری تعیین کند. سقف خروجی یک نوبت ۲۰ action و ۱۲۸ هزار نویسه متن است. در یک نتیجه، بیش از یک تغییر ری‌اکشن برای یک پیام پذیرفته نمی‌شود.
- قرارداد قدیمی `text/reply_to_id` برای سازگاری fakeها و داده‌های قبلی باقی مانده؛ پیش‌فرض قدیمی آن ریپلای به آخرین پیام است. ترکیب آن با actionها رد می‌شود. قرارداد جدید پیش‌فرض بدون ریپلای دارد.
- همه actionها پیش از ذخیره اعتبارسنجی می‌شوند؛ یک action نامعتبر کل نتیجه را رد می‌کند. وضعیت موفق job و تمام intentهای خروجی با هم commit می‌شوند.
- متن‌ها به ترتیب با کلید مستقل هر action و بخش ارسال می‌شوند؛ شکست یا unknown بخش قبلی، ادامه زنجیره متن را تا تعیین تکلیف متوقف می‌کند. ری‌اکشن مستقل از زنجیره متن است و نامعتبر بودن ری‌اکشن در تلگرام جلوی پیام‌ها را نمی‌گیرد.
- ری‌اکشن جدید یک هدف، intent قدیمی هنوز pending برای همان هدف را جایگزین می‌کند تا retry قدیمی ری‌اکشن تازه را برنگرداند. unknown خودکار تکرار نمی‌شود. ویرایش یا لغو job، intentهای pending آن را نامعتبر می‌کند.
- فعلاً ری‌اکشن ایموجی استاندارد یا حذف آن پشتیبانی می‌شود؛ custom و paid در قرارداد ابزار وجود ندارند. پشتیبانی ایموجی در گروه، نوع پیام و محدودیت‌های سرور هنگام ارسال مشخص می‌شود؛ خطای قطعی وضعیت failed می‌گیرد و به موفقیت تبدیل نمی‌شود.
- migration `0003` خروجی‌های قبلی را با نوع message حفظ می‌کند و مقصد ریپلای را nullable می‌کند. downgrade در حضور تاریخچه غیرقابل نمایش در schema قبلی رد می‌شود.

نتیجه بررسی این تکمیل: **۷۴ تست آفلاین موفق**، Ruff check و format check موفق، mypy strict بدون خطا روی ۳۶ فایل منبع. تست‌ها شامل چند مقصد، پیام عادی، reaction-only و حذف ری‌اکشن، رد کل خروجی نامعتبر، خطاهای تلگرام، ادامه پس از restart و ارتقای دیتابیس دارای خروجی pending هستند. ارسال زنده تلگرام همچنان به فاز شش موکول است.
