# تحویل فاز سوم — پرونده و حافظه مستند

تاریخ: ۲۰۲۶-۱۱-۱۸. حافظه مستقل از عمر نشست ساخته شده است؛ اجرای نمونه و تست‌ها آفلاین‌اند. نصب CLI، ورود واقعی، ارزیابی درک مدل و آزمایش سرویس‌ها در فاز شش باقی می‌مانند.

## اجرا

از ریشه checkout:

```bash
source .venv/bin/activate
uv sync --locked --group dev
uv run python -m peyda_pm_bot --phase-three --database /tmp/peyda-memory-demo.db
uv run ruff check .
uv run ruff format --check .
uv run mypy src/peyda_pm_bot
uv run pytest
```

دمو با agent برنامه‌ریزی‌شده، ثبت تصمیم ورود، تغییر بحث به پرداخت، restart، بازیابی با منبع و اصلاح تصمیم را از همان مسیر عمومی حافظه اجرا می‌کند. این سناریو صحت ذخیره/بازیابی را نشان می‌دهد؛ تشخیص معنایی یا رعایت توافق تیم توسط مدل واقعی را ثابت نمی‌کند. برای دموهای سه فاز دیتابیس جدا انتخاب کنید، چون project IDهای نمونه متفاوت‌اند.

## پرونده و سابقه

`MemoryRecord` انواع case، note، link، summary و architecture_draft دارد. یادداشت به proposal، decision، commitment، question یا interpretation دسته‌بندی می‌شود. هر نسخه شامل عنوان، متن، وضعیت، پرونده‌های مرتبط، aliasها، نسخه‌های دقیق پیام منبع، افراد منتسب و دلیل تغییر است. زمان ثبت UTC نگهداری می‌شود.

پیوند یک پیام می‌تواند چند پرونده را پوشش دهد؛ هویت پیوند از chat/message ID ساخته می‌شود و منبع آن یک update ID دقیق است. اصلاح پیوند، نسخه قبلی را نگه می‌دارد. خلاصه‌ها منابع پوشش‌داده‌شده دارند؛ مدل باید پوشش را صریح اعلام کند و در صورت نیاز خلاصه را در چند رکورد یا نسخه نگه دارد. خلاصه جای متن اصلی یا ابزار منابع نیست.

`status=inactive` با دلیل، رکورد را از نتایج فعال جست‌وجو کنار می‌گذارد؛ حذف فیزیکی ابزار ندارد. history نسخه‌های پیشین را با `superseded=true` مشخص می‌کند. ویرایش پیام منبع، داده وابسته و خلاصه‌های مربوط را نیازمند بازبینی می‌کند. تغییر یادداشت یا اصلاح پیوند نیز خلاصه‌های موجود همان پرونده‌ها را stale می‌کند؛ ایجنت باید آن‌ها را دوباره بررسی کند.

منابع، نام و شناسه گوینده، sender chat، تاپیک، reply و زمان را از پیام ذخیره‌شده برمی‌گردانند. انتساب فرد باید به گوینده‌ای در منابع ارجاع داشته باشد؛ هویت ارسال از طرف chat به فرد انسانی تبدیل نمی‌شود. فرضیات یا پیشنهادهای خود ایجنت با category مناسب و منبع بحث ثبت می‌شوند، نه با منبع ساختگی.

متن architecture_draft تنها در دیتابیس قرار می‌گیرد؛ به پوشه یا فایل مخزن پیدا دسترسی نوشتن داده نشده است.

## ابزارهای MCP

SDK رسمی `mcp==1.30.0` در uv.lock قفل شده است. چهار ابزار stdio ارائه می‌شوند:

| ابزار | ورودی اصلی | خروجی |
|---|---|---|
| `memory_search` | turn_token، query، evidence اختیاری، cursor/limit | نتایج پرونده و یادداشت، یا شواهد پیام‌ها |
| `memory_read` | turn_token، record_id، history اختیاری، cursor/limit | پرونده و رکوردهای مرتبط، یا سابقه نسخه‌ها |
| `memory_sources` | turn_token، update_ids، cursor/limit | متن و مشخصات نسخه‌های دقیق پیام |
| `memory_prepare` | turn_token، operation_key، record، expected_revision | تغییر آماده‌شده، با وضعیت staged_until_successful_turn |

برای ثبت جدید expected_revision صفر است. ابزار شناسه و revision جدید را برمی‌گرداند؛ برای اصلاح، id موجود و expected_revision فعلی ارسال شوند. فیلد revision جزو بدنه record ورودی ابزار نیست. برای retry همان operation_key و ورودی یکسان استفاده شود؛ تکرار با محتوای متفاوت رد می‌شود.

نمونه آماده‌سازی یک تصمیم، پس از ساخت پرونده و دریافت شناسه واقعی آن:

```json
{
  "turn_token": "grant-from-current-agent-request",
  "operation_key": "login-decision-1",
  "expected_revision": 0,
  "record": {
    "kind": "note",
    "title": "روش ورود",
    "text": "ورود با شماره تلفن",
    "category": "decision",
    "case_ids": ["case-id-returned-by-memory-prepare"],
    "source_update_ids": [10],
    "attributed_user_ids": [7]
  }
}
```

شناسه‌ها در مثال آزمایشی‌اند؛ مدل باید از شناسه پیام‌های واقعاً ذخیره‌شده و خروجی ابزار استفاده کند. رد یک منبع ناموجود، مجوز ساخت آن یا تغییر خودکار تصمیم نیست.

هر نوبت grant تصادفی خودش را دارد. فقط hash آن در دیتابیس ذخیره می‌شود و repr درخواست آن را نشان نمی‌دهد. سرور به یک project/database مشخص متصل است؛ ابزار ورودی پروژه، مسیر فایل، SQL یا shell ندارد. در هر فراخوانی، grant و running بودن job با revision/generation کنترل می‌شوند. پس از لغو، unknown، supersede، commit یا retry قبلی، grant قدیمی قابل استفاده نیست.

برای client مستقل آزمایشی می‌توان سرور را پس از initialize برنامه اصلی اجرا کرد:

```bash
uv run python -m peyda_pm_bot.adapters.memory.server --database /path/to/initialized.db --project project-id
```

سرور migration، outbox recovery یا claim جدید اجرا نمی‌کند؛ این‌ها فقط متعلق به برنامه اصلی‌اند. بدون grant نوبت فعال، ابزار قابل استفاده نیست. bootstrap تنظیم سرور را به `session/new` و `session/load` همان ACP session می‌دهد؛ مسیر live همچنان به تأیید محدودسازی محیط در فاز شش وابسته است. stderr برای log و stdout فقط برای MCP است.

## تراکنش و بازیابی

ابزار نوشتن ابتدا تغییر را با job، revision، generation و operation_key آماده می‌کند. خواندن همان نوبت تغییرات آماده‌شده خودش را می‌بیند؛ سایر نوبت‌ها و حافظه قطعی آن‌ها را نمی‌بینند.

worker پس از پایان موفق، اعتبار نوبت را دوباره بررسی و در یک Unit of Work این موارد را ثبت می‌کند: نسخه‌های حافظه، پایان job، خروجی‌های ایجنت و اعلان‌های ثبت یادداشت. خروجی نامعتبر یا شکست commit تمام این تغییرات را rollback می‌کند. تکرار sender هیچ عملیات حافظه‌ای را دوباره اجرا نمی‌کند.

اعلان ثبت یادداشت‌های مستند تجمیع می‌شود؛ آخرین تغییر هر یادداشت در نوبت اعلام می‌شود. پیوند، index و خلاصه داخلی به‌تنهایی اعلان جدید نمی‌سازند. نوبت silent نیز می‌تواند تغییر حافظه داشته باشد؛ در این حالت اعلان ثبت برنامه از outbox ارسال می‌شود.

تغییرات staged مربوط به نوبت لغوشده یا unknown وارد حافظه قطعی نمی‌شوند. سابقه آماده‌سازی برای پیگیری باقی می‌ماند؛ شروع تلاش جدید grant قبلی را abandoned و محیط staged جدیدی ایجاد می‌کند. تصمیم درباره تکرار نتیجه unknown همچنان با کنترل صریح مرحله قبل است.

## سیاست تیم، جست‌وجو و محدودیت‌ها

سیاست پیش‌فرض متنی در `application/memory/policy.py` تعریف شده است. با `PEYDA_MEMORY_POLICY_PATH` می‌توان فایل UTF-8 مستقل پروژه را جایگزین کرد؛ فایل در startup خوانده می‌شود و برای نوبت‌های همان اجرای برنامه ثابت است. hash و متن دقیق سیاست در هر memory turn ثبت می‌شوند.

سیاست تیم سه‌نفره است: ثبت توافق روشن، سؤال در ابهام، تأیید پیش از کنارگذاشتن تصمیم و حداقل دو تأیید برای موارد حساس. موارد حساس اختصاصی هنوز تعریف نشده‌اند؛ متن پیش‌فرض از ایجنت می‌خواهد در ابهام سؤال کند. هیچ جدول رأی، شمارش تأیید یا نقش مدیر محصول برای این قواعد ساخته نشده است. admin IDs موجود فقط کنترل‌های فنی بات را نگه می‌دارند. تأیید واقعی رعایت این دستورالعمل‌ها نیازمند ارزیابی مدل در فاز شش است.

جست‌وجو با شناسه/alias دقیق، سپس عنوان و متن انجام می‌شود؛ هم‌رتبه‌ها با زمان ثبت و شناسه پایدار مرتب می‌شوند. «ی/ي»، «ک/ك»، فاصله و نیم‌فاصله برای query/index منطقی یکسان می‌شوند؛ متن اصلی تغییر نمی‌کند. پیش‌فرض ۱۰ نتیجه، حداکثر صفحه ۲۰ و سقف پاسخ ابزار ۱۲ هزار نویسه است. cursor با تغییر نتایج نامعتبر می‌شود؛ فراخوانی باید از صفحه اول تکرار شود.

سقف هر رکوردِ serializeشده ۱۰ هزار نویسه، متن ۸ هزار نویسه، منابع ۱۰۰، پرونده‌های مرتبط و aliasها هرکدام ۲۰، و تغییرات هر نوبت ۵۰ است. رکورد بزرگ رد می‌شود، نه اینکه بی‌صدا بریده شود. جست‌وجوی فعلی برای شروع، رکوردها/شواهد محلی را اسکن می‌کند؛ benchmark مقیاس بزرگ انجام نشده است.

آزمون اولیه FTS5 روی «ورود کاربری» با query عربی «كاربري» بدون normalization صفر و پس از normalization یک نتیجه داد. به همین دلیل FTS5 خام مبنای محصول نشد؛ جست‌وجوی فعلی به FTS5 یا دیتابیس برداری وابسته نیست. ارزیابی عملکرد و کیفیت معنایی گسترده ادعا نمی‌شود.

## شواهد تحویل

۹۴ تست آفلاین موفق، Ruff و format check و mypy strict؛ ارتباط واقعی یک client MCP با سرور stdio محلی نیز تست شده است. سناریوها: source و speaker نامعتبر، project اشتباه، grant دیررس، read-after-write، idempotency، revision stale، تاریخچه و soft removal، پیوند چندپرونده و اصلاح، خلاصه stale، rollback حافظه/job/outbox، restart، retry isolation، بودجه و pagination، سیاست ممیزی‌شده و نبود نوشتن فایل مخزن.

دموی برنامه دو startup مستقل را طی کرد و تصمیم را با منبع بازیابی و اصلاح کرد. CLI واقعی Antigravity، Telegram و GitHub استفاده نشدند؛ CI روی GitHub اجرا نشده است.

منابع قرارداد: [SDK رسمی MCP Python](https://github.com/modelcontextprotocol/python-sdk)، [راه‌اندازی و بارگذاری نشست ACP با MCP servers](https://agentclientprotocol.com/protocol/v1/session-setup) و امضاهای بسته‌های قفل‌شده MCP/ACP نصب‌شده. نتیجه آزمایش local MCP، تأیید پشتیبانی CLI نصب‌نشده Antigravity نیست.
