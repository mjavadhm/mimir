# قرارداد معماری و توسعه Peyda PM Bot

وضعیت: قرارداد معماری؛ فازهای یک تا چهار پیاده‌سازی آفلاین دارند. قابلیت‌های فازهای بعد هنوز اجرا نشده‌اند.

هدف، ساخت یک برنامه ماژولار با Ports & Adapters سبک است که بتوان آن را در تغییرات کوچک توسعه داد. اول بات مدیریت قابل استفاده تحویل می‌شود؛ ریویو PR پس از آن اضافه می‌شود. [پلن اجرا](IMPLEMENTATION_PLAN.md) ترتیب تحویل و [README](../README.md) رفتار محصول را مشخص می‌کنند.

## ۱. مالکیت قابلیت‌ها

ساختار لایه‌ای پلن حفظ می‌شود؛ هر لایه براساس قابلیت تقسیم می‌شود. مثلاً منطق پیام در `domain/conversations`، هماهنگی آن در `application/conversations` و ذخیره‌سازی آن در `adapters/storage/conversations` قرار می‌گیرد. این نام‌ها مقصد طراحی‌اند؛ پوشه و کلاس فقط هنگام نیاز ساخته می‌شوند. برای هر قابلیت یک مسیر اصلی داریم، نه دو ساختار موازی feature-first و layer-first.

| مالک | قواعد و داده‌های تحت مالکیت | مرز ارتباط |
|---|---|---|
| `conversations` | هویت پیام و گوینده، نسخه ویرایش، reply، topic و گروه‌بندی گفتگو | ورودی نرمال‌شده و ارجاع پیام برای سایر قابلیت‌ها |
| `memory` | پرونده، خلاصه، تصمیم، پیشنهاد، شواهد و سابقه جایگزینی | جست‌وجو/خواندن و تغییر نسخه‌دار پرونده |
| `work` | تسک، مسئول، وابستگی، مانع، معیار پایان و ارتباط ایشو/PR | use caseهای مدیریت و تصویر وضعیت کار |
| `actions` | پیش‌نویس عملیات، تأیید، اعتبار نسخه، تلاش اجرا و نتیجه | تنها مسیر اجرای عملیات اثرگذار مدیریتی |
| `runtime` | inbox/outbox، job، checkpoint، worker و عمر نشست | زمان‌بندی و تحویل کار؛ بدون تصمیم‌گیری درباره اولویت تجاری یا معنای پیام |
| `reviews`، مرحله دوم | نسخه PR، checkpoint بررسی و یافته‌ها | استفاده از قرارداد حافظه/کار و همان executor و worker |

گیت‌هاب مرجع رسمی وضعیت ایشو/PR است؛ داده محلی آن‌ها projection همراه زمان/نسخه آخرین تطبیق است. تصمیم گفتگو و رابطه پیام با پرونده، مرجع محلی دارند. مسیر تطبیق نباید اطلاعات قدیمی گیت‌هاب را روی تغییر تازه اعمال کند؛ تعارض نامطمئن برای بازبینی ثبت می‌شود.

## ۲. جهت وابستگی و رابط‌های عمومی

- `domain`: مدل‌ها و قواعد مستقل از framework و I/O. ORM، aiogram، subprocess و شبکه وارد این لایه نمی‌شوند.
- `application`: use caseها و قراردادهای کوچک I/O مربوط به همان قابلیت؛ به domain وابسته است و adapter واقعی را import نمی‌کند.
- `adapters`: تبدیل داده بیرونی و پیاده‌سازی قراردادها. handler ورودی را اعتبارسنجی و use case را فراخوانی می‌کند؛ قانون تأیید یا ساخت تسک را خودش اجرا نمی‌کند.
- `runtime`: اجرای use caseها از طریق وابستگی تزریق‌شده، کنترل lifecycle و زمان‌بندی. شیء runtime نباید به مدیر همه قواعد محصول تبدیل شود.
- `bootstrap`: تنها محل اتصال پیاده‌سازی‌های واقعی؛ configuration، connection و worker در آن ساخته و با lifecycle مشخص بسته می‌شوند. import یک ماژول، شبکه، فایل یا task را راه نمی‌اندازد.

هر قابلیت، API عمومی کوچک در application دارد؛ تغییر داده قابلیت دیگر فقط از این مسیر مجاز است. import مدل ذخیره‌سازی یا فراخوانی repository داخلی قابلیت دیگر ممنوع است. نیاز به هماهنگی چند قابلیت با یک use case هماهنگ‌کننده مشخص حل می‌شود؛ handler و repository یکدیگر را صدا نمی‌زنند. وابستگی چرخه‌ای با جابه‌جایی قرارداد یا تغییر مسئولیت حل می‌شود، نه lazy import برای پنهان‌کردن چرخه.

DTOهای عبوری از مرزها typed و فاقد مدل framework هستند. `dict[str, Any]` برای عبور دادن همه جزئیات بین لایه‌ها قرارداد قابل قبول نیست. برای داده قابل اعتماد داخلی dataclass/enum و برای ورودی غیرقابل اعتماد اعتبارسنجی در مرز کافی است؛ مدل مشابه را بدون تفاوت واقعی در هر لایه تکرار نکنید.

## ۳. قرارداد ایجنت

application فقط مفهوم‌های «اجرای کار»، «لغو»، «رویداد متن»، «درخواست اجازه» و «پایان/شکست» را می‌شناسد؛ نام روش JSON-RPC و شکل payload مخصوص Antigravity در adapter می‌ماند.

هر اجرا `job_id`، شناسه نشست، نسخه درخواست و رویدادهای قابل اتصال به همان اجرا دارد. قابلیت resume و ابزارهای حافظه باید به‌صورت capability تأییدشده ثبت شوند؛ adapter اجازه ندارد فقدان یک قابلیت را با موفقیت ساختگی پنهان کند. رویداد permission باید شناسه درخواست و پاسخ معتبر داشته باشد؛ پاسخ نامربوط یا دیررس مجوز نیست.

fake agent فقط همان قرارداد عمومی را پیاده می‌کند؛ منطق محصول جداگانه‌ای در fake ساخته نمی‌شود. موفقیت fake، تأیید API واقعی نیست. با درخواست کاربر در ۲۰۲۶-۱۱-۱۸، نصب CLI و بررسی اتصال واقعی جلو افتاده است؛ پذیرش نهایی کامل همچنان مستقل است. شواهد در [آزمون اتصال](LIVE_TESTING.md) ثبت می‌شوند.

## ۴. یک مسیر برای اقدام اثرگذار

برای ساخت/تغییر ایشو، تعیین مسئول یا موعد و ثبت تصمیم رسمی، مسیر زیر یک بار پیاده می‌شود:

`propose → validate → approve when required → claim → execute → reconcile/result → notify`

- نوع اقدام، مقصد، actor، نسخه درخواست/پیش‌نویس، منبع و شناسه پایدار اقدام ثبت می‌شوند. نیاز به تأیید از policy نقش/عملیات می‌آید؛ تمام عملیات الزاماً تأیید دستی نمی‌خواهند.
- handler، ابزار ایجنت و قابلیت آینده حق دورزدن این مسیر را ندارند. خواندن اطلاعات یا ثبت خام پیام، عملیات تأییدخواه نیست.
- claim با انتقال وضعیت شرطی و بررسی نسخه انجام می‌شود. تغییر actor، مقصد یا payload تأیید قبلی را معتبر نگه نمی‌دارد.
- پیش از ارسال شبکه وضعیت دوباره بررسی می‌شود. لغو پس از شروع ارسال ممکن است دیر رسیده باشد؛ نتیجه باید با وضعیت واقعی تطبیق داده شود.
- timeout پس از ارسال می‌تواند `unknown` باشد. شناسه محلی dedup معادل idempotency تضمین‌شده سرویس بیرونی نیست؛ قبل از retry باید نتیجه بررسی شود.
- اعلان از outbox ارسال می‌شود. شکست ارسال اعلان نمی‌تواند action موفق را دوباره اجرا کند. غیرفعال‌شدن ظاهری دکمه جای اعتبارسنجی سرور را نمی‌گیرد.

## ۵. مرز تراکنش و Unit of Work

repositoryها commit مستقل نمی‌کنند. use case مرز تراکنش را تعیین می‌کند و adapter ذخیره‌سازی، commit/rollback را انجام می‌دهد. برای تغییر چند repository در یک عملیات، Unit of Work سبک با session همان عملیات استفاده می‌شود؛ UoW سراسری یا generic CRUD framework لازم نیست.

| عملیات | بخش اتمیک محلی | خارج تراکنش |
|---|---|---|
| دریافت ورودی | inbox و checkpoint/offset مربوط | درخواست بعدی شبکه و تأیید دریافت |
| ثبت تصمیم | تصمیم، شواهد/نسخه و اعلان موردنیاز | ارسال اعلان |
| قبول تأیید | بررسی actor/نسخه، ثبت approval و انتقال وضعیت | اجرای شبکه |
| پایان اقدام | وضعیت نتیجه، شناسه خارجی و outbox | ارسال تلگرام |

هر تراکنش کوتاه و مالک یک session است؛ انتظار مدل، شبکه یا انسان در آن قرار نمی‌گیرد. داده‌ای که هنگام اجرای طولانی تغییر می‌کند با revision بررسی می‌شود. تغییر schema در migration است؛ `create_all` یا تغییر پنهانی schema در startup جای migration را نمی‌گیرد.

## ۶. پایداری، خطا و زمان

- یک اجرای agent در کل پروژه: قفل asyncio به‌تنهایی جلوی دو پردازش را نمی‌گیرد. قفل نمونه برنامه و مدیریت child باقی‌مانده بخشی از طراحی runtime است.
- taskهای پس‌زمینه owner، timeout و shutdown مشخص دارند؛ task رهاشده و retry نامحدود ممنوع‌اند.
- خطاها به نامعتبر/غیرمجاز، موقت قابل retry، نتیجه نامعلوم و خطای داخلی تفکیک شوند. retry فقط برای وضعیت مناسب، با سقف و رعایت محدودیت سرویس است.
- `CancelledError` پس از cleanup دوباره منتشر شود. `except Exception: pass` یا تبدیل خطا به خروجی موفق ممنوع است.
- timestamps ذخیره‌شده UTC و timezone-aware هستند. elapsed time درون یک اجرا با ساعت monotonic و deadline پایدار با زمان قابل بازیابی مدیریت می‌شود؛ clock برای آزمون تزریق‌پذیر است.
- log برای پیگیری `event_id / job_id / action_id` دارد؛ payload کامل، token و متن خصوصی پیش‌فرض log نمی‌شوند. همین شناسه‌ها در آزمون recovery قابل تطبیق‌اند.

## ۷. روال توسعه برای جلوگیری از انباشت کد نامنسجم

پیش از هر تغییر، README، فاز فعال و ماژول صاحب قابلیت را بررسی کنید. ابتدا مسیر موجود را جست‌وجو کنید و همان را توسعه دهید. اگر مسیر مشابهی پیدا شد، دلیل نیاز به مسیر دوم باید روشن شود.

هر تغییر کوچک باید رفتار قابل مشاهده، owner، قرارداد ورودی/خروجی، اثر بر schema و حالت شکست مشخص داشته باشد. تغییر چند قابلیت مستقل را برای راحتی تولید کد در یک کار ادغام نکنید. یک قابلیت از handler تا ذخیره‌سازی و آزمون تحویل شود؛ صرف ایجاد پوشه یا کلاس پیشرفت محصول محسوب نمی‌شود.

برای dependency، abstraction یا الگوی جدید، مسئله واقعی و جایگزین ساده‌تر را ثبت کنید. interface برای هر کلاس، repository پایه همه‌منظوره، service locator، event bus و microservice پیش‌فرض نیستند. اجزای مشترک فقط با مصرف‌کننده واقعی استخراج شوند؛ `utils.py` محل جمع‌کردن منطق بی‌مالک نیست.

اگر یک تصمیم معماری مهم تغییر کرد، دلیل، گزینه کنارگذاشته‌شده و پیامد آن در سند تصمیم کوتاه ثبت و پلن همزمان اصلاح شود. تغییر ساختار نباید دو معماری نیمه‌تمام باقی بگذارد. مرجع قواعد اجرایی این سند است؛ در اسکیل‌ها یا فایل‌های متعدد نسخه دیگری از همان قانون ایجاد نکنید.

## ۸. کنترل‌هایی که هنگام پیاده‌سازی اضافه می‌شوند

- بررسی خودکار جهت importها: domain مستقل، application بدون adapter، دسترسی بین قابلیت‌ها فقط از قرارداد عمومی و ممنوعیت چرخه وابستگی.
- تست رفتار با fake transport؛ تست تراکنش، unique constraints، migration و recovery با SQLite فایل‌محور موقت. fake نباید تفاوت اثرگذار با storage واقعی را پنهان کند.
- تست‌های critical: rollback تصمیم و outbox با هم؛ تأیید stale؛ claim همزمان؛ دریافت دوباره update؛ restart؛ نتیجه unknown؛ اعلان ناموفق؛ عدم اجرای دو کار ایجنت.
- Ruff و mypy و تست مرتبط در هر تحویل؛ CI همان دستورهای محلی را اجرا کند. هیچ suppression گسترده برای عبور خروجی تولیدشده از ابزارها اضافه نشود.
- تغییرات فقط اسناد به تست محصول نیاز ندارند؛ صحت لینک و سازگاری تصمیم‌ها بررسی شود.

تعریف پایان هر بخش: معیار پذیرش فاز برقرار، تست رفتار/شکست مربوط موفق، migration لازم بررسی‌شده، مرزهای معماری حفظ‌شده و وضعیت واقعی در مستندات ثبت‌شده باشد. تست شبیه‌سازی و تست زنده در گزارش تفکیک شوند؛ قابلیت تأییدنشده کامل اعلام نشود.

## تصمیم‌های فاز دو

بسته گفتگو واحد انتقال است و تمام بسته‌ها به همان نشست می‌روند. پاسخ عادی ACP متن Markdown است و بعد از پایان نوبت به یک پاسخ ثبت‌شده در outbox تبدیل می‌شود. خروجی ساخت‌یافته برای چند پیام، انتخاب مقصد ریپلای، ری‌اکشن یا سکوت به کار می‌رود و اعتبارسنجی typed دارد. با شروع هر نوبت یک پیام rich تازه، به‌صورت ریپلای به آخرین پیام همان نوبت، در تاپیک ثبت می‌شود و فقط همان پیام با مرحلهٔ کوتاه کار ویرایش می‌شود. فکر داخلی و متن ناتمام پاسخ منتشر نمی‌شوند. پس از ثبت پاسخ نهایی، همان پیام وضعیت حذف می‌شود. پیش‌نویس streaming مخصوص چت خصوصی است و در گروه استفاده نمی‌شود.

درخواست Turbo و وضعیت مؤثر آن جدا ثبت می‌شوند. `--serve` به‌صورت پیش‌فرض Turbo را برای ابزار ساخت فایل پروژه فعال می‌کند. ابزار هم در مرز ACP و هم هنگام اجرا، مجوز نوبت فعال را بررسی می‌کند. `/turbo on` و `/turbo off` برای مدیران کنترلی عمل می‌کنند. در ری‌استارت، مقدار تنظیمات سرویس مبنای وضعیت اولیه است.


در تکمیل فاز دو (۲۰۲۶-۱۱-۱۸)، نتیجه ایجنت به فهرست `SendMessage` و `SetReaction` گسترش یافت. validation کل فهرست و اعتبار مقصد در domain انجام می‌شود؛ adapter ACP فقط مدل بیرونی را تبدیل می‌کند. تمام intentها در همان تراکنش نتیجه job وارد outbox می‌شوند و sender تنها مسیر اجرای ارتباط تلگرام است. مسیر مستقیم ارسال از ایجنت وجود ندارد. ریپلای هر پیام اختیاری است؛ سیاست لحن، جمع‌بندی یا انتخاب ری‌اکشن مستقل از وجود این ابزارهاست.


## تصمیم‌های فاز سه

MemoryService مرز عمومی قابلیت حافظه است. source evidence از قرارداد عمومی conversations خوانده می‌شود؛ حافظه به repository داخلی گفتگو وابسته نیست. ابزار MCP به project/database ثابت متصل است و هر درخواست به grant نوبت، job revision و generation معتبر نیاز دارد. سرور ابزار هیچ migration یا recovery را اجرا نمی‌کند.

تغییرها در turn-scoped staging ذخیره می‌شوند. worker تنها مسیر commit است: اعتبار نوبت، کنترل revision و منابع، ثبت نسخه حافظه و پایان job و اعلان‌های outbox در یک تراکنش. وضعیت staged به معنای ثبت قطعی نیست؛ unknown یا لغو، staged را به حافظه منتشر نمی‌کند. تاریخچه، منبع و stale بودن داده حفظ می‌شوند.

توافق تیمی، حساسیت تصمیم و شرط دو تأیید در متن سیاست هستند؛ به خواسته صریح کاربر، کد نه رأی می‌شمارد و نه برای این قواعد approval engine ایجاد می‌کند. نقش مدیر محصول جدا فرض نمی‌شود. شناسه مدیران کنترلی بات مربوط به عملیات فنی است. پیش‌نویس معماری فقط در حافظه نگهداری می‌شود و ابزار نوشتن فایل پروژه ندارد.


## تصمیم‌های فاز چهار

چرخه grant از حافظه به SqlTurns و قرارداد مشترک authorize_turn منتقل شد؛ جدول تاریخی memory_turns و wrapperهای سازگار حافظه حفظ شدند. حافظه و GitHub یک نوبت، grant و job revision/generation را مصرف می‌کنند؛ سیستم permission موازی ایجاد نشده است.

work صاحب projection و case links و metadata کار، و actions صاحب پیش‌نویس، صف، تلاش و نتیجه است. شبکه فقط از executor و adapter انجام می‌شود. پیش‌نویس و submit تا پایان موفق job staged می‌مانند. memory، انتشار actionها، نتیجه job و اعلان‌ها در Unit of Work مشترک‌اند. executor مستقل از worker ایجنت است و نشست دوم ایجاد نمی‌کند.

ابزارهای MCP GitHub داخل پردازش اصلی با HTTP loopback هستند؛ credential به ایجنت منتقل نمی‌شود. مخزن در دیتابیس و payload action ثابت است. API بدون تضمین exactly-once یا CAS مستند شده؛ marker و reconciliation محافظه‌کارانه جای این تضمین‌ها را نمی‌گیرند.

طبق انتخاب کاربر، توافق تیم و حساسیت عملیات GitHub هم در پرامپت هستند؛ ready را با تأیید انسانی اشتباه نگیرید. ابزارهای نوشتن فقط مدیریت ایشو و کامنت author تنظیم‌شده را پوشش می‌دهند. مرج، review، کد و تنظیمات مخزن ابزار نوشتن ندارند.

## تصمیم‌های فاز پنج

گزارش از همان projection کار و یادداشت‌های ثبت‌شدهٔ حافظه ساخته می‌شود. `/report` داخل تراکنش پردازش ورودی نتیجه را به outbox می‌دهد. worker تازه‌سازی، GitHub را بیرون تراکنش می‌خواند و آخرین مشاهده و پوشش آن را همراه دادهٔ محلی ذخیره می‌کند. نوبت روزانه، وضعیت اعلان‌شده و خروجی زمان‌بندی‌شده در یک تراکنش ثبت می‌شوند و sender همان مسیر ارسال و رسیدگی به نتیجهٔ نامعلوم را استفاده می‌کند.

بکاپ و بازیابی فرمان‌های محلی و مستقل از runtime هستند. بکاپ با API SQLite گرفته می‌شود و پس از بررسی به‌صورت اتمیک در مسیر تازه منتشر می‌شود. جزئیات تنظیم و تمرین در [راهنمای فاز پنجم](PHASE_FIVE.md) آمده است.

## تصمیم‌های آزمون اتصال زودهنگام

تاپیک تلگرام رابط گفت‌وگوی ماندگار Antigravity است. راه‌اندازی زنده روت پروژه و شناسهٔ یک گفت‌وگوی موجود را از تنظیمات می‌گیرد. شناسهٔ صریح بر شناسهٔ به‌جامانده از تست scratch مقدم است و پس از load موفق در دیتابیس ثبت می‌شود. تلاش بعدی هم همان شناسه را بارگذاری می‌کند. خطای load راه‌اندازی را متوقف می‌کند. این قرارداد مربوط به بازکردن همان گفت‌وگوی ذخیره‌شده است و همگام‌سازی زنده با TUI را پوشش نمی‌دهد.

فرمان‌های صریح doctor، discovery، تست سلامت تلگرام و تست ایجنت به bootstrap تعلق دارند و از همان use caseها استفاده می‌کنند. discovery فقط مختصات پیام `/peyda_setup` را نشان می‌دهد؛ offset نمی‌فرستد، ACK نمی‌کند و نقش خودکار اعطا نمی‌کند. قفل دریافت براساس bot ID مانع polling هم‌زمان حالت‌های تست می‌شود. تست سلامت namespace و دیتابیس جدا دارد تا صف محصول را پردازش نکند.

بات `agy-cli` را از مسیر معمول با cwd پروژه اجرا می‌کند. تنظیمات مجوز ویژهٔ پردازش بات را با `--settings` می‌فرستد و فایل تنظیمات شخصی را بازنویسی نمی‌کند. بات درخواست‌های مجوز خواندن را بر اساس مسیر واقعی فایل و محدودهٔ پروژه بررسی می‌کند. آزمون زنده نشان داد بعضی خواندن‌های CLI هیچ درخواستی به بات نمی‌فرستند. مجوز MCP به ابزار ثبت‌شده، نشست و نوبت فعال وابسته است. `--live-agent` مسیر تلگرام، ایجنت و حافظه را اجرا می‌کند و گیت‌هاب در تست جداگانه بررسی می‌شود.

`project_create_file` فایل متنی تازه را اتمیک و با رد مسیرهای نمادین و مقصد موجود در روت پروژه ایجاد می‌کند. نتیجه با شناسهٔ نوبت ثبت می‌شود. عملیات ساخت واقعی فایل بلافاصله با موفقیت ابزار رخ می‌دهد و لغو بعدی نوبت آن را برنمی‌گرداند. ویرایش، حذف و اجرای shell در این ابزار در دسترس نیستند.

نسخهٔ ۱٫۵٫۱۰ با نام `Antigravity ACP Server`، HTTP MCP را در initialize اعلام نمی‌کند؛ فراخوانی واقعی ابزار HTTP در این نسخه تأیید شد. این جفت نام/نسخه یک استثنای مستند capability است؛ نسخه‌های ناشناخته بدون اعلان HTTP رد می‌شوند. نبود capability به‌طور عمومی نادیده گرفته نمی‌شود. این تصمیم جایگزین افزودن یک proxy stdio موازی شد، چون transport فعلی عملاً کار می‌کند.

دسترسی به keyring لینوکس یک گزینهٔ صریح و پیش‌فرض خاموش است؛ فقط با `agent_desktop_keyring=true` آدرس DBus و XDG runtime به child منتقل می‌شود. این اجازه به معنی تضمین محدودشدن سرویس keyring به credential خاص نیست. توکن‌های سرویس‌های محصول به child منتقل نمی‌شوند. شکست نوبت و اعلان بدون payload خصوصی نیز در یک تراکنش ثبت می‌شوند؛ لغو یا revision قدیمی اعلان شکست جدید تولید نمی‌کند.
