# آزمون اتصال زودهنگام

تاریخ: ۲۰۲۶-۱۱-۱۸. کاربر پس از فاز چهار، نصب و تست واقعی را جلو انداخت. این checkpoint جای پذیرش کامل محصول، فاز پنج یا آزمون همهٔ شکست‌های فاز شش را نمی‌گیرد.

بات اکنون CLI را در روت پروژه و با پروفایل معمول اجرا می‌کند. برای این نصب، کاربر `moshtari-yab` را انتخاب کرد و شناسهٔ گفت‌وگو از فهرست محلی CLI برای همان روت تنظیم شد. پروفایل اختصاصی و scratch مربوط به آزمون قبلی بودند.

## شواهد واقعی

| مسیر | نتیجهٔ مشاهده‌شده |
|---|---|
| CLI رسمی Linux x64 | نسخهٔ ۱٫۵٫۱۰ نصب و SHA512 آرشیو با manifest رسمی تطبیق داده شد؛ launcher گرافیکی `agy` تغییر نکرد |
| ACP | initialize، ساخت نشست و یک prompt واقعی با پاسخ موردانتظار موفق شدند |
| HTTP MCP | CLI ابزار آزمایشی ping را از سرور داخل پردازش اصلی فراخواند؛ HTTP در handshake اعلام نشده است |
| تلگرام | getMe و getWebhookInfo موفق؛ webhook خالی؛ پیام setup گروه، تاپیک و هویت فرستنده را مشخص کرد |
| گروه | supergroup دارای forum و بات administrator است؛ Privacy Mode فعال، ولی بات به‌دلیل مدیر بودن می‌تواند گفتگو را بگیرد |
| GitHub | ورود موجود و دسترسی به مخزن انتخابی تأیید؛ HttpGithub واقعاً ایشوها، لیبل‌ها و assigneeها را خواند |
| پیام `/health` و پاسخ در تاپیک | دریافت واقعی، outbox با وضعیت sent و پاسخ قابل مشاهده در Telegram Web تأیید شد |
| ACP و حافظه از مسیر برنامه | یک job کنترل‌شده با ایجنت واقعی و خروجی تلگرام fake موفق شد؛ جای تست گروه را نمی‌گیرد |
| مسیر تلگرام ← ایجنت ← حافظه ← پاسخ | آزمون `PEYDA-PM-73` در تاپیک واقعی `pm` موفق شد. ورودی در SQLite ثبت و پردازش شد، نشست موجود `moshtari-yab` یک بار `memory_search` را کامل کرد و job موفق شد. تلگرام پیام ریپلای، پیام مستقل و ری‌اکشن 👍 را پذیرفت و هر سه در Telegram Web دیده شدند. |
| کنترل مجدد GitHub | همان ایشوی آزمایشی #1 با آداپتور برنامه خوانده شد و وضعیت `closed` تأیید شد. این اجرا فقط خواندنی بود. |
| نوشتن GitHub | ایشوی تستی #1 از ActionService و ActionExecutor ساخته و بسته شد؛ موفقیت هر دو عملیات و بسته‌بودن نهایی تأیید شد |
| resume نشست و ورود | CLI واقعی با پروفایل معمول همان گفت‌وگوی `moshtari-yab` را باز کرد. پس از فعال‌سازی دسترسی، لاگ تأیید کرد که CLI از ورود ذخیره‌شده در Keyring استفاده کرد. |
| ذخیره و ویرایش تلگرام بعد از restart | Telegram Bot API پیام `PEYDA-EDIT-83` و رویداد ویرایش آن را تحویل داد. بعد از بستن و بازکردن همان SQLite آزمایشی، متن دقیق هر دو نسخه، فرستنده، گروه و تاپیک حفظ شده بود. بازپخش همان دو update نسخهٔ دیگری نساخت. |
| فهم کد | ایجنت در روت `moshtari-yab` تابع کوتاه ساختگی را خواند، خروجی دو مسیر تابع را درست محاسبه کرد و رشته‌ای را که فقط در فایل بود برگرداند. |
| محدودیت خواندن | **ناموفق.** `read_file` فایل ساختگی خارج از روت زیر `/tmp` را بدون درخواست permission از بات خواند. دو تکرار با override `strict` و سپس `strict` همراه با منع صریح `read_file(*)` هم همین نتیجه را داشتند. هیچ فایل واقعی بیرون روت در این آزمون هدف نبود. |
| جلوگیری از ویرایش فایل موجود | بات درخواست `edit_file` را با `reject_once` رد کرد و محتوای فایل ساختگی تغییر نکرد. CLI بعد از رد، پاسخ JSON معتبر نداد و بات اعلان شکست نوبت ساخت. ساخت فایل تازه سناریوی جداگانه‌ای برای پذیرش بعدی است. |
| رفتار مدیریتی | با ورودی ساختگی و مدل واقعی، بات برای گفت‌وگوی معمولی سکوت کرد و پیشنهاد اولیه و نسخهٔ ویرایش‌شدهٔ آن را به‌عنوان تصمیم ثبت نکرد. در درخواست مبهم برای کنارگذاشتن تصمیم، تأیید و دلیل خواست و تصمیم فعال ماند. |
| ثبت و بازیابی تصمیم | از سه پیام ساختگیِ سه گوینده، یک پرونده و یک تصمیم با سه منبع ثبت و اعلان ایجاد شد. پس از راه‌اندازی مجدد با همان SQLite، `memory_search` و `memory_read` تصمیم را بازیابی کردند. متن پاسخ روز و ساعت درست را گفت، ولی برای منبع شناسهٔ داخلی داد. |

در آزمون سیاست مدیریتی، رویدادهای تلگرام ساختگی و خروجی تلگرام محلی بود. CLI، MCP و SQLite واقعی بودند. یک اجرای اولیهٔ پیشنهاد با مهلت کوتاه ۵۰ ثانیه به `unknown` رسید. در اجرای مجدد با مهلت ۱۰۵ ثانیه، سناریوهای پیشنهاد، ثبت، بازیابی و درخواست مبهم موفق شدند. هر ۱۴۸ آزمون آفلاین و بررسی‌های Ruff و mypy موفق شدند.

تنظیمات واقعی بات در `.env` محلی با دسترسی 0600 قرار دارند. CLI از محل معمول ورود خودش استفاده می‌کند. فایل `.env`، دیتابیس‌ها و `.runtime` و `.tools` در gitignore قرار دارند. تست‌های روتین بدون استفاده از تنظیمات واقعی بات اجرا می‌شوند.

## اجرا از پوشهٔ پروژه

نام عمومی CLI برابر `agy-cli` است. روی این لپتاپ symlink در `~/.local/bin` به باینری داخل پروژه اشاره دارد و جابه‌جایی پروژه نیاز به اصلاح لینک دارد. اگر از قبل به CLI وارد شده‌اید، همان پروفایل استفاده می‌شود. برای ورود معمول CLI در صورت نیاز این فرمان را در ترمینال اجرا کنید.

```bash
./scripts/agy-login
```

کد OAuth را در ترمینال خودتان وارد کنید. در لینوکس ممکن است خود پردازش بات برای استفاده از ورود ذخیره‌شده به دسترسی Keyring نیاز داشته باشد.

ابتدا فقط `PEYDA_BOT_TOKEN` در `.env` کافی است:

```bash
.venv/bin/python -m peyda_pm_bot --doctor
.venv/bin/python -m peyda_pm_bot --discover-telegram
```

برای discovery، poller دیگری روشن نباشد و کاربر از حساب غیرناشناس در تاپیک هدف `/peyda_setup` بفرستد. فقط مختصات همین پیام نمایش داده می‌شود؛ پیام‌های خصوصی چاپ نمی‌شوند. offset حذف شده و هیچ ACK فرستاده نمی‌شود. فقط ۱۰۰ update ابتدای صف قابل مشاهده‌اند؛ نبودن پیام، به معنی خالی‌بودن صف نیست. کشف شناسه به‌تنهایی نقش مدیر ایجاد نمی‌کند؛ شناسه‌های تأییدشده باید صریح در `.env` تنظیم شوند.

پس از تنظیم project/group/topic/admin/database براساس `.env.example`:

```bash
.venv/bin/python -m peyda_pm_bot --live-telegram --duration 300
```

از همان حساب مجاز در همان تاپیک `/health` بفرستید. پاسخ موردانتظار: «سرویس فعال است؛ ذخیره‌سازی محلی در دسترس است.» دیتابیس پیش‌فرض `.runtime/telegram-smoke.db` با namespace جداست؛ انتخاب دیتابیس محصول به‌جای آن رد می‌شود. ورودی‌های این تست فقط در همین دیتابیس ذخیره می‌شوند. ایجنت و executor گیت‌هاب اجرا نمی‌شوند.

پس از توقف تست سلامت، `PEYDA_AGENT_WORKSPACE_PATH` را روی روت پروژه و `PEYDA_AGENT_CONVERSATION_ID` را روی شناسهٔ گفت‌وگوی موجود آن تنظیم کنید. اجرای بات همان گفت‌وگو را با ACP بارگذاری می‌کند.

```bash
.venv/bin/python -m peyda_pm_bot --live-agent --duration 600
```

این حالت از دیتابیس تنظیم‌شدهٔ محصول و یک نشست ACP استفاده می‌کند. در تاپیک یک درخواست آزمایشی برای جست‌وجوی حافظه و پاسخ بفرستید. ابزارهای حافظه واقعی‌اند؛ گیت‌هاب غیرفعال است، حتی اگر مشخصات آن در `.env` وجود داشته باشد. یک poller برای هر bot ID اجرا می‌شود؛ SIGINT، SIGTERM و پایان duration منابع را می‌بندند. نبودن duration یعنی اجرا تا زمان توقف دستی.

CLI به نسخهٔ تست‌شده محدود است. بات درخواست‌های permission رسیده برای فایل و MCP را بررسی می‌کند. MCP به allow-once برای نام دقیق ابزار ثبت‌شده و نوبت فعال نیاز دارد. آزمون زنده نشان داد خواندن داخلی CLI می‌تواند بدون ارسال چنین درخواستی انجام شود. رفتار فعلی خواندن مورد قبول کاربر است و محدودسازی اضافهٔ آن شرط پذیرش اجرای زنده نیست.

روی لینوکس، اعتبار OAuth ممکن است در Secret Service ذخیره شود. supervisor به‌صورت پیش‌فرض DBus و XDG_RUNTIME_DIR را منتقل نمی‌کند. گزینهٔ `PEYDA_AGENT_DESKTOP_KEYRING=false` پیش‌فرض است. برای نصب محلی، با اجازهٔ کاربر آن را فعال کردیم و دریافت پاسخ معتبر مدل در نشست موجود را آزمودیم. این متغیرها دسترسی پردازش به سرویس Keyring نشست را فراهم می‌کنند. توکن‌های Telegram/GitHub از محیط پردازش CLI فیلتر می‌شوند.

تست GitHub از ورودی کنترل‌شدهٔ محلی و مجوز مشخص کاربر برای همان عنوان/متن استفاده کرد؛ این نتیجه به معنی فعال‌بودن ابزار GitHub در گروه نیست. [ایشوی آزمایشی بسته‌شده](https://github.com/mjavadhm/divar-mcp/issues/1). نتیجهٔ create از پاسخ پایدار action خوانده شد؛ فهرست ایشوها بلافاصله بعد از ایجاد هنوز آن را نشان نمی‌داد، بنابراین نبودن فوری در list را نباید شکست create دانست یا باعث ساخت دوباره کرد.

## خطا و محدودیت

خطای validation فقط نام فیلدها را نشان می‌دهد؛ متن خطای بیرونی، URL دارای توکن و payload خصوصی چاپ نمی‌شوند. در خطای اتصال، توکن/شبکه، webhook، عضویت، حالت forum و Privacy Mode را با doctor بررسی کنید. آزمون زندهٔ `PEYDA-PM-73` به یک پیام مشخص از مدیر مجاز و یک دیتابیس موقت محدود شد و offset خارجی را جلو نبرد. در این آزمون نوشتن GitHub از تلگرام و سناریوهای قطع شبکه اجرا نشدند.

نسخهٔ ۱٫۵٫۱۰ برای HTTP MCP یک استثنای مشخص دارد: قابلیت در initialize نیست ولی call واقعی موفق بود. مجوزهای MCP قبلاً همگی رد می‌شدند؛ اکنون فقط ابزارهای مشخص حافظه/گیت‌هاب در نشست و نوبت فعال مجازند. unknown server/version بدون capability همچنان رد می‌شود.

شکست نوبت ایجنت اکنون اعلان پایدار و بدون متن خصوصی، همراه job ID و دستور retry دارد؛ کارت «آماده» دیگر تنها نشانهٔ قابل مشاهده نیست. ثبت وضعیت شکست و اعلان در یک تراکنش است و اعلان تکراری تولید نمی‌شود.

مراجع: [نصب رسمی](https://antigravity.google/cli/install.sh)، [ACP](https://antigravity.google/docs/ide/extensions/acp/)، [قواعد permission](https://antigravity.google/docs/permissions)، [Bot API](https://core.telegram.org/bots/api). signature روش‌های استفاده‌شده با پکیج نصب‌شدهٔ aiogram 3.32.0 نیز بررسی شد.

## اجرای یکپارچه روی سرور

`--serve` همان مدیر نشست، پردازش تلگرام، outbox، executor گیت‌هاب و worker زمان‌بندی را در یک پردازش راه می‌اندازد. نمونهٔ unit در [peyda-pm.service](../scripts/peyda-pm.service) است. مسیر پروژه و محل دیتابیس در unit مطابق سرور مقصد تنظیم شوند. قبل از راه‌اندازی با همان کاربری که سرویس را اجرا می‌کند به Antigravity وارد شوید و روت پروژه و شناسهٔ گفت‌وگوی موجود را در محیط سرویس تنظیم کنید. مجوز توکن GitHub باید با مخزن تنظیم‌شده و قابلیت‌های موردنیاز مطابقت داشته باشد. `PEYDA_GITHUB_LIVE_VALIDATED=true` پس از اعتبارسنجی این مجوزها، اجرای executor را برای همان مخزن مجاز می‌کند.

```bash
.venv/bin/python -m peyda_pm_bot --serve
```

`PEYDA_AGENT_TURBO=true` در حالت سرویس پیش‌فرض است. در این حالت، Antigravity ابزار `project_create_file` را در نوبت فعال بدون تأیید جداگانه فراخوانی می‌کند. فایل متنی تازه در یک دایرکتوری موجود داخل روت ایجاد می‌شود و بازنویسی و عبور از مسیر نمادین مردود است. Turbo اینجا سیاست ابزارهای خود بات است. شل عمومی و تأیید سراسری CLI فعال نیستند. ساعت گزارش و یادآوری با تنظیم `PEYDA_REPORT_AT` و `PEYDA_REMINDER_AT` فعال می‌شود. روت خواندن با رفتار فعلی CLI پذیرفته شده است.

### شواهد پذیرش فاز شش

- در آزمون `PEYDA-P6-127` یک پیام دقیق از تاپیک واقعی `pm` به SQLite موقت رفت. CLI نسخهٔ ۱٫۵٫۱۰ همان گفت‌وگوی موجود را بارگذاری کرد و ابزارهای واقعی `memory_search`، `github_read` و `project_create_file` موفق شدند.
- خواندن ایشوی آزمایشی و همگام‌سازی GitHub واقعی و فقط‌خواندنی بودند. ساخت فایل در پوشهٔ موقت انجام شد و متن آن بررسی شد. یک گزارش زمان‌بندی‌شده در outbox ثبت و محلی تحویل شد.
- بات در تلگرام همان درخواست را ریپلای کرد، پیام دوم را مستقل منتشر کرد و روی پیام ورودی 👍 گذاشت. آزمون فقط ورودی آزمایشی را پردازش کرد و offset تلگرام را جلو نبرد.
- ۱۶۷ تست خودکار، Ruff، mypy و اعتبارسنجی unit نمونه موفق شدند. تست‌های خودکار شامل رد بازنویسی و خروج از روت، کنترل Turbo، دوام صف و راه‌اندازی مجدد هستند.
- نصب روی سرور مقصد، رفتار در قطعی یا sleep/wake واقعی روی همان میزبان، اجرای یک‌روزه و نوشتن GitHub از مسیر یکپارچهٔ تلگرام هنوز پذیرش زنده ندارند.

### اصلاح پاسخ عادی Antigravity

در سرویس فعال، پاسخ متنی نوبت ۶ به‌دلیل `json_invalid` کنار گذاشته شد. مسیر پاسخ عادی اکنون Markdown می‌پذیرد و پس از پایان نوبت، یک پیام rich ثبت می‌کند. تست آفلاین مسیر کامل ACP تا outbox و Bot API شبیه‌سازی‌شده را بررسی کرده است. ۱۷۱ تست، Ruff و mypy موفق شدند. تحویل rich در گروه واقعی در این اجرا هنوز تأیید نشده است.
