# مرحله دوم محصول — افزودن ریویو PR

وضعیت: برنامه آینده؛ اجرا پس از تحویل و تست واقعی [بات مدیریت پروژه](IMPLEMENTATION_PLAN.md). ریویو PR شرط پذیرش یا استفاده از بات مدیریت نیست.

## محدوده

در مرحله اول، بات تصمیم‌ها، تسک‌ها، مسئول‌ها، موانع و وضعیت ایشو/PR را مدیریت می‌کند. این مرحله قابلیت تحلیل تغییرات کد، سنجش معیارهای انجام و انتشار review در گیت‌هاب را به همان بات اضافه می‌کند. یک ایجنت، یک نشست مشترک و یک کار فعال همچنان پابرجاست.

نیازمندی کامل محصول در بخش ۱۲ [README](../README.md) حفظ شده است. هنگام شروع این مرحله، قراردادها و مستندات سرویس‌ها دوباره بررسی می‌شوند. نصب مجدد CLI پیش‌نیاز نیست؛ نسخه و سازگاری اتصال موجود بررسی می‌شود.

## فازهای این مرحله

### فاز یک — رویداد PR و نسخه دقیق کد

- دریافت رویدادهای بازشدن PR و push از polling گیت‌هاب؛ cursor هم‌پوشان، dedup و تجمیع تغییرات پیاپی. افزودن webhook در صورت نیاز پشت همان ورودی.
- اضافه‌کردن migration داده‌های اختصاصی ریویو، نسخه‌ها و checkpointها؛ نگهداری داده و عملکرد بات مدیریت هنگام ارتقا.
- ثبت repository، شماره PR، base SHA و head SHA؛ snapshot مستقل بدون تغییر برنچ پوشه کاری کاربر.
- اتصال PR به ایشو، معیار پایان، پرونده موضوع و قوانین پروژه؛ در ابهام درخواست روشن‌سازی.

**تحویل آفلاین:** یک رویداد تکراری کار اضافه نسازد، pushهای پیاپی به جدیدترین نسخه منتهی شوند و snapshot روی نسخه دقیق قرار بگیرد.

### فاز دو — ریویوی مرحله‌ای و انتشار کنترل‌شده

- اجرای مراحل محدود بررسی محدوده/معیارها، diff، شواهد تست و CI و تولید یافته‌های قابل اقدام.
- استفاده از همان worker و نشست؛ بررسی صف مدیریت بین مراحل و زمان‌بندی منصفانه برای پیشرفت گفتگو و ریویو.
- checkpoint هر مرحله، timeout و retry محدود؛ جلوگیری از انتشار نتیجه منقضی پس از تغییر base/head یا تصمیم مرتبط.
- ابزارهای محدود خواندن کد و انتشار review از executor با policy مشخص؛ متن PR و فایل‌ها داده ورودی‌اند. اجرای تست کد ناشناس فقط در محیط محدود مجاز است.
- خروجی شامل یافته با فایل/محل/شواهد، وضعیت پوشش معیارها، تغییر خارج محدوده و خلاصه اقدام بعدی در تلگرام.
- بازبینی تازگی SHAها بلافاصله پیش از انتشار؛ PR مرتبط ولی ناقص باعث بستن ایشو نشود. مرج انسانی باقی می‌ماند.

**تحویل آفلاین:** fake agent و transport، سناریوهای تغییر نسخه، لغو، خروجی نامعتبر، نتیجه نامعلوم API و شکست ارسال را پوشش دهند؛ قابلیت‌های مدیریت رگرسیون نداشته باشند.

### فاز سه — یکپارچه‌سازی و تست واقعی ریویو

- بررسی مجوز انتشار review روی مخزن آزمایشی و اجرای جریان واقعی PR در همان بات فعال.
- آزمایش push یا تغییر base وسط ریویو، قطع نشست، ری‌استارت، تغییر تصمیم مرتبط و پرسش مدیریتی همزمان.
- ارزیابی کیفیت یافته‌ها روی PRهای دارای ایراد مشخص و PR سالم؛ صرف تولید متن، اثبات صحت ریویو نیست.
- اندازه‌گیری تأخیر پاسخ مدیریت و پیشرفت ریویو، منابع مصرفی و تنظیم اندازه مراحل.

**تحویل:** معیارهای بخش ۱۲ README و سناریوهای زیر در محیط واقعی بررسی شوند، ناسازگاری‌ها رفع و تست‌های انجام‌نشده صریح ثبت شوند.

## سناریوهای پذیرش اختصاصی

| سناریو | انتظار |
|---|---|
| تغییر head یا base | منقضی‌شدن نتیجه قبلی و بازبینی نسخه جدید |
| گفتگو هنگام ریویوی طولانی | پردازش بین مراحل و حفظ پیشرفت ریویو |
| چند رویداد برای یک نسخه | یک کار مؤثر برای آن نسخه |
| ری‌استارت وسط مرحله | بازیابی checkpoint بدون دو اجرای ایجنت |
| قطع پاسخ گیت‌هاب پس از انتشار | تطبیق نتیجه پیش از تکرار |
| شکست ارسال خلاصه تلگرام | retry اعلان بدون review تکراری |
| PR مرتبط ولی ناقص | اعلام معیارهای باقی‌مانده و بازماندن ایشو |
| دستور مخرب در کد/توضیح PR | عدم تغییر policy یا دورزدن executor |
| ارتقای دیتابیس و فعال‌شدن ریویو | حفظ تسک‌ها، حافظه و قابلیت‌های مدیریتی |

آزمون‌های آفلاین در فاز توسعه همان قابلیت اجرا می‌شوند؛ تست زنده این مرحله در فاز آخر خودش انجام می‌شود.
