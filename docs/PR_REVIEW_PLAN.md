# فاز پنج میمیر — ریویوی درخواستی PR

| بخش | مسیر اجرا و معیار پذیرش |
|---|---|
| 5a · تنظیم نشست‌ها | هنگام شروع، میمیر دستور مدیریت را از `prompts/mimir.md` و دستور ریویو را از `prompts/reviewer.md` می‌خواند. فهرست سرورهای HTTP هر نقش در `config/mcp.toml` قرار دارد. تغییرها را با ری‌استارت بین نوبت‌ها اعمال کنید. برای پذیرش، یک دستور موقت را به پرامپت اضافه کنید، پاسخ مشخص آن را در تلگرام ببینید و دستور را بردارید. |
| 5b · درخواست و بررسی | پیام تیم در تاپیک، شماره یا لینک PR را مشخص می‌کند. میمیر با `review_pr` درخواست را ثبت می‌کند. پس از پایان موفق نوبت مدیریت، کارگر شناسهٔ نشست اختصاصی و SHAهای مبنا و سرشاخه را ثبت می‌کند. کارگر عنوان و شرح PR، فایل‌های تغییرکرده و patchهای موجود، درخواست تیم و اطلاعات ایشوهای لینک‌شده را در snapshot جداگانه به ریویوکننده می‌دهد. نشست مدیریت هم‌زمان قابل‌استفاده است. |
| 5c · تحویل و انتشار | نتیجه با شناسهٔ ریویو و نسخهٔ بررسی‌شده در پاسخ به پیام تیم می‌آید. انتشار کامنت معمولی GitHub با درخواست صریح تیم، همان ابتدا یا بعداً با `publish_review` انجام می‌شود. درخواست لغو از `cancel_review` می‌گذرد. |

هر درخواست با نسخهٔ پیام تلگرام و شمارهٔ PR شناخته می‌شود. بازپخش ابزار کار دوم نمی‌سازد. یک push به‌تنهایی ریویو راه نمی‌اندازد. تغییر base یا head حین بررسی باعث اجرای دوباره برای درخواست جاری می‌شود. اگر تیم بعداً انتشار نتیجهٔ قدیمی را بخواهد، باید ریویوی تازه درخواست کند. درست پیش از POST، نسخه دوباره از گیت‌هاب خوانده می‌شود. GitHub برای کامنت عادی شرط اتمی روی SHA ارائه نمی‌کند و تغییر در فاصلهٔ خواندن تا نوشتن ممکن است.

نشست، پرامپت ثابت و هش آن، وضعیت کار، نتیجه و اقدام انتشار در SQLite باقی می‌مانند. پس از وقفه، بررسی از آخرین checkpoint ادامه می‌یابد. اگر فقط تحویل تلگرام باقی مانده باشد، متن ذخیره‌شده از صف ارسال می‌شود. پس از پاسخ نامعلوم GitHub، جست‌وجوی خواندنی بر اساس حساب منتشرکننده و نشانگر اقدام انجام می‌شود. در جست‌وجوی ناموفق یا ناقص، وضعیت نامعلوم حفظ می‌شود.

پوشش snapshot به داده‌های در دسترس API بستگی دارد. فایل باینری یا patch حذف‌شده می‌تواند بدون متن باشد. سقف دریافت فایل‌ها ۳۰۰۰ فایل و ۴ مگابایت patch است. ریویوکننده محدودیت شواهد را همراه نتیجه اعلام می‌کند. گزارش وضعیت CI، نتیجهٔ اجرای تست محلی یا مجوز مرج محسوب نمی‌شود.

نتیجه‌های آفلاین و مشاهدات واقعی هر تحویل در [گزارش پذیرش](LIVE_TESTING.md) ثبت می‌شوند. تست پیگیری PR در `tele-agy` تا اولین PR واقعی همان مخزن معلق است.
